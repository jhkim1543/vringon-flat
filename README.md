# VRINGON FLAT

**제품 사진 한 장 → 플랫 스케치 → 파트별 레이어 분리 → Illustrator `.ai` 자동 생성**

디자이너가 테크팩을 그릴 때 하는 일 — 사진을 평면 도식으로 옮기고, 파트마다 레이어를
나누고, 벡터로 다시 그리는 일 — 을 파이프라인으로 만든 것입니다.
결과물은 Illustrator에서 바로 열려서 파트별로 색·형태를 수정할 수 있습니다.

**▶ 데모 · V4.1 Semantic Topology · V3.2 도면 기반 벡터 · V2 레이어 SVG · API 문서: https://jhkim1543.github.io/vringon-flat/**

<sub>신발 · 가방 · 주얼리를 중심으로 검증했고, 의류·안경·시계·가구 등 11개 카테고리와
분류 밖의 물건도 처리합니다.</sub>

## 빠르게 써 보기

```bash
git clone https://github.com/jhkim1543/vringon-flat
cd vringon-flat
npm install
cp .env.example .env      # OPENAI_API_KEY / GEMINI_API_KEY / FAL_KEY 입력
npm run dev:api           # → http://localhost:5201
```

브라우저에서 `http://localhost:5201/demo/` — 데모 화면이 그대로 뜨고, **직접 실행** 탭에서
내 이미지를 넣어 볼 수 있습니다. 웹 UI가 따로 필요하면 `npm run dev`(Vite 포함).

```bash
# API로 바로 쓰기
curl -X POST http://localhost:5201/v1/jobs -F "image=@sneaker.jpg" -F "categoryHint=footwear"
# → {"id":"…","statusUrl":"…","pollAfterMs":5000}

curl http://localhost:5201/v1/jobs/<id>          # status: running → done
curl -o result.ai http://localhost:5201/v1/jobs/<id>/file/ai
```

한 건에 **2~5분**이 걸립니다(생성 모델 2종 + 분해 + 벡터화). 그래서 동기 응답이 아니라
잡을 만들고 폴링하는 방식입니다.

## API

전체 명세는 [`docs/openapi.yaml`](docs/openapi.yaml) (OpenAPI 3.1)이고,
읽기 좋은 문서는 [데모 페이지의 API 탭](https://jhkim1543.github.io/vringon-flat/#api)에 있습니다.

| 엔드포인트 | 하는 일 |
|---|---|
| `POST /v1/jobs` | 이미지 업로드 → `202 {id}` (백그라운드 실행) |
| `GET /v1/jobs/{id}` | 진행률·단계·QA 지표·결과 파일 URL |
| `GET /v1/jobs/{id}/file/{ai\|svg\|jsx\|ir}` | 산출물 다운로드 |
| `GET /v1/jobs` | 최근 잡 목록 |
| `GET /v1/health` | 엔진·키·한도 (인증 불필요) |

**인증** — `.env`의 `API_KEYS`를 채우면 `X-API-Key` 헤더가 필수가 됩니다.
비워 두면 인증 없이 열립니다(로컬 개발 기본값). **공개 배포 시 반드시 설정하세요.**

**산출물 4종**

| 종류 | 내용 |
|---|---|
| `.ai` | PDF 호환 + OCG 레이어. Illustrator에서 바로 열림 |
| `.jsx` | Illustrator 스크립트. 실행하면 **네이티브 `.ai`** 생성 (레이어 패널 완전 지원) |
| `.svg` | 웹 미리보기·타 툴 반입 |
| `.ir.json` | Vector IR — 레이어→그룹→패스 구조를 코드로 다룰 때 |

`.ai`를 두 가지로 내보내는 이유: PDF-OCG 방식은 어디서나 열리지만 Illustrator의
레이어 패널과 완전히 같지는 않습니다. 네이티브 레이어가 필요하면 `.jsx`를 실행하세요.

## 파이프라인

```
0  입력 정규화 · 배경 격리 · 복수 객체 분리
1  이미지 이해        → Layer Plan (카테고리 · 파트 목록 · 그룹 구조)
2  플랫 스케치 생성    → 2개 모델 × (라인아트 · 컬러플랫)
3  후보 자동 평가      → 실루엣 IoU · 엣지 · 색 순도
4  amodal 레이어 분해  → 가려진 부분까지 복원한 파트별 레이어
5  재합성 QA · 자가교정 → 어긋난 곳을 그 자리에서 고침
6  레이어별 벡터화     → 면은 윤곽 추적, 선은 중심선 추출
7  패스 정리·검증      → 깨진 패스 제거, 앵커 과다 경고
8  .ai / .jsx / .svg / IR 생성
```

### 왜 사진을 바로 벡터화하지 않는가

사진에는 그림자·반사·직물 질감이 있고, 벡터화기는 그걸 전부 형상으로 봅니다.
메시 운동화 한 켤레가 8,000개가 넘는 패스가 됩니다.
플랫 스케치로 한 번 옮기면 **평면 색면 + 윤곽선**만 남아, 이후 단계가 다뤄야 할 대상이
분명해집니다. 면과 선을 같은 이미지에서 뽑기 때문에 선이 면과 어긋나지도 않습니다.

### 레이어 분해 — 도구를 각자 잘하는 범위에서만

| 도구 | 하는 일 | 한계 (실측) |
|---|---|---|
| amodal 분해 | 가려진 부분까지 복원한 재질 단위 레이어 | 파트 **이름을 모름**, 레이어끼리 겹침 |
| 색 클러스터 + 연결요소 | 같은 재질이 떨어져 있으면 별개 파트 | 색만 보면 토캡/힐카운터가 뭉침 |
| SAM 3 | 일반 명사 경계 보정 | `sole` `shoelace` `tongue`은 되지만 `vamp` `quarter`는 마스크 0개 |
| 비전 모델 + 규칙 | 조각에 파트 이름 배정 | 모델이 죽으면 규칙(위치·크기·색 사전)이 대신함 |

### QA가 파이프라인 안에 있다

레이어를 실제 색으로 다시 쌓아 플랫과 대조하고, 어긋난 곳을 **그 자리에서 고칩니다**:
덮이지 않은 전경 회수 · 색이 다른 덩어리 분리 · 이름 없는 잔재 정리.
최종 지표는 API 응답의 `qa` 필드로 나옵니다.

| 지표 | 뜻 | 통과 기준 |
|---|---|---|
| `coverage` | 전경 중 레이어가 덮은 비율 | ≥ 0.8 |
| `spill` | 배경을 침범한 비율 | ≤ 0.08 |
| `colorDeltaE` | 재합성 평균 색차 (0~441) | ≤ 60 |

**샘플 9종 실측** (전부 통과)

| 샘플 | 커버리지 | 배경 침범 | 색차 ΔE | 레이어 | 패스 |
|---|---:|---:|---:|---:|---:|
| shoe_1 | 99.7% | 1.0% | 6.7 | 13 | 278 |
| shoe_2 | 99.8% | 0.1% | 9.5 | 24 | 943 |
| shoe_3 | 100% | 0.3% | 6.5 | 16 | 412 |
| bag_1 | 100% | 0.9% | 10.9 | 14 | 109 |
| bag_2 | 99.5% | 1.0% | 2.1 | 10 | 91 |
| bag_3 | 99.2% | 0.4% | 14.0 | 9 | 1,099 |
| jewelry_1 | 99.8% | 0.2% | 4.3 | 12 | 116 |
| jewelry_2 | 96.0% | 0.4% | 10.0 | 25 | 251 |
| jewelry_3 | 88.4% | 0.0% | 18.2 | 22 | 263 |

## 임의의 이미지를 넣어도 되는가

0단계가 어떤 입력이든 파이프라인의 전제("흰 배경을 꽉 채운 제품 한 점")로 맞춥니다.

- EXIF 회전 · 알파 채널 · CMYK/16bit → sRGB · 애니메이션 첫 프레임
- 배경이 있으면 제품만 오려내고, 제품이 작게 찍혔으면 크롭 (화면 14% 점유일 때 색이 전부 어긋났음)
- 한 화면에 신발 2개·반지 3개가 있으면 **인스턴스별로 따로 처리**해 하나의 `.ai`로 합침
- 종횡비 6:1을 넘거나 손상된 파일은 `400`으로 거절

어느 단계가 실패해도 산출물은 나옵니다. amodal 분해가 비면 플랫 색분해로, 이름 배정이
실패하면 `Region N`으로, 한쪽 이미지 모델이 죽으면 다른 쪽으로 진행합니다.

## 배포

```bash
docker build -t vringon-flat .
docker run -p 5201:5201 --env-file .env -v $PWD/outputs:/app/outputs vringon-flat
```

운영 시 확인할 것:

- `API_KEYS` 설정 (미설정 = 인증 없음)
- `MAX_CONCURRENT_JOBS` — 외부 모델 비용·레이트리밋 때문에 기본 2. 초과 요청은 `429`
- `outputs/`는 계속 쌓입니다. 볼륨으로 빼고 주기적으로 정리하세요
- 잡 목록은 **메모리에 있습니다**. 서버를 재시작하면 `GET /v1/jobs/{id}`는 404가 되지만
  산출물 파일은 디스크에 남습니다

## 개발

```bash
npm run dev          # API + 웹 UI
npm run typecheck
npm run smoke        # 과금 없는 스모크 테스트

npx tsx server/rebuild.ts <jobId>     # 생성 API 재호출 없이 분해~벡터화만 다시
npx tsx server/analyze.ts <jobId>     # 실루엣 IoU · 앵커 밀도 · 레이어 중복
npx tsx server/export-demo.ts         # docs/samples 갱신
npx tsx server/export-demo-v3.ts      # docs/samples-v3 갱신
npx tsx server/export-demo-v4.ts      # docs/samples-v4 갱신

npx tsx server/run-v4.ts <이미지> <이름> --category shoe   # V4 (Semantic Topology)

npx tsx server/run-v3.ts <이미지> <이름> --category shoe   # V3 (도면 → 라인 벡터)
```

`rebuild.ts`는 이미 만들어진 잡의 플랫 이미지와 amodal 캐시를 재사용하므로
**재과금 없이** 분해·벡터화 로직을 반복 검증할 수 있습니다. 파이프라인을 고칠 때 이걸 씁니다.

벡터 뷰어: `http://localhost:5201/viewer?job=<8자리>` — 레이어 토글, 채움/외곽선/앵커 3뷰.

## 알려진 제약

- 파트 **이름**은 비전 모델이 없으면 위치·색 규칙으로만 붙어 거칩니다 (`Region N`이 남을 수 있음).
- 메시·비즈처럼 반복 질감이 많은 제품은 선 패스가 많아져 Illustrator가 무거워집니다.
- 한 장의 사진에서 보이지 않는 면(바닥·안감)은 만들 수 없습니다.
- 잡 목록이 메모리에 있어 서버 재시작 시 상태 조회가 끊깁니다(파일은 남음).

## V4.5 — 주얼리 반사 제거 · 촘촘한 점 정리

### 주얼리: 도면에 사진의 하늘 반사가 그대로 남아 있었다

VRINGON 도면은 주얼리를 그릴 때 스톤 안쪽에 사진의 반사를 그대로 옮긴다(jewelry_3 세 스톤
전부 파란 대리석 무늬). 벡터화하면 그것이 검은 파편 수백 개가 된다. 테크팩에서 반사는
**조명의 산물이지 제품의 형상이 아니다.**

`server/v4/gemFlatten.ts` 가 그것을 지운다. 다섯 번 고쳐 쓴 자리라 각 선택에 근거가 있다.

| 시도 | 결과 |
|---|---|
| 파트 마스크를 침식해 안쪽 잉크 삭제 | 마스크가 실제 스톤과 어긋난 곳에서 얼룩이 그대로 남았다(중앙·후면 스톤) |
| 신장률로 패싯 능선만 보존 | 하늘 반사의 **줄무늬도 길쭉하다** — 능선 행세를 하고 살아남았다 |
| → **도면의 닫힌 면에 뚫린 구멍**으로 잡는다 | 마스크 정합과 무관해졌다. 반사 = 면에 뚫린 구멍 |
| 구멍을 전부 메움 | 베젤 안쪽 링까지 구멍으로 잡혀 **금속 테가 사라졌다**(47,546px 삭제) |
| → 큰 구멍 · 면을 두르는 고리는 보존 | 테는 면 bbox 의 70% 이상을 감싼다. 반사 조각은 짧은 호다 |

패싯 능선은 남긴다 — 면을 가로지를 만큼 길고(지름의 45% 이상) 곧고(≤5%) 가는 것만.
컷 스톤의 능선은 제품의 형상이다.

**카테고리로 막아야 한다.** `bead` 는 주얼리에서는 진주 알이지만 가방에서는 소재 그
자체다 — 게이트 없이 돌렸더니 bag_2 "Beaded pouch body" 가 보석으로 잡혀 비즈 조직이
통째로 지워졌다(패스 671 → 136). 이제 주얼리 카테고리에서만 돈다.

### 촘촘한 점: 보이지 않는 구멍이 서브패스를 수천 개로 만들고 있었다

비즈·메시 도면의 배경 면은 알 하나마다 구멍이 뚫려 컴파운드 패스 하나에 서브패스가
수천 개가 된다(bag_2 `f8` 이 **2,739개**). Illustrator 에서 그 패스는 통째로만 선택되므로
사실상 편집이 불가능하다.

그런데 **그 구멍은 보이지 않는다.** 알 자체는 그 위에 따로 그려지고(패턴·프리미티브),
구멍 아래에 있는 것은 흰 배경뿐이다. 바깥 윤곽 대비 0.1% 미만인 구멍만 메운다.

| bag_2 | 이전 | 지금 |
|---|---:|---:|
| 서브패스 | 3,628 | **888** |
| 한 패스 최대 서브패스 | 2,739 | **108** |
| 앵커 | 20,068 | **8,312 (−59%)** |
| F@0 · 선F@2 · 디테일 · 구멍 | 0.734 · 0.941 · 0.979 · 182→159 | **전부 동일** |

지우는 것이 아니라 **덮이는 것을 안 그리는 것**이라 충실도가 한 자리도 안 변한다.

### 지표 하나를 일관되게 고쳤다

`failingMajorParts` 는 이미 얇은 파트를 경계 F1 로 재고 있는데 `misassigned` 만 면
precision 을 쓰고 있었다. 끈·체인은 면적이 거의 없어 기준 마스크가 조각뿐이고, 제대로
그린 기하도 "밖"으로 세어진다. 같은 규칙으로 맞췄다.

## V4.4 — 레이어 분리 감사: "충분히 나뉘었나"를 직접 물었다

9종 전부를 레이어 관점으로 감사했다(`server/v4/layer-audit.ts`). 의미 gate 의 IoU 와는
다른 질문이다 — 디자이너가 레이어 패널에서 하는 일(켜고 끄고, 골라 고치고, 하나만 빼기)이
되는가.

### 감사 결과: 나뉘지 않았다

| | V4.3 | 문제 |
|---|---:|---|
| 빈 파트 (자기 기하 0) | **14 / 64 (22%)** | 레이어 패널에 아예 없다 |
| 자기 선이 없는 파트 | **23 / 64 (36%)** | 면만 있고 윤곽은 남의 것 |
| 한 파트 최대 독점 | **93%** (jewelry_1 ring_body) | 나머지가 그 안에 갇혔다 |

원인은 하나였다. **`assignByCurve` 가 패스 전체를 다수결로 한 파트에 통째 배정한다.**
제품 선화는 외곽·시임·끈·로고가 서로 닿아 하나의 거대한 성분이 되므로, 거기서 나온
컴파운드 패스 하나가 통째로 한 레이어에 들어갔다. 딥리서치가 "라우팅 단위가 connected
component 라 너무 크다"고 지적한 그 P1 이고, 레이어 문제의 **직접 원인**이었다.

### 고친 것 — 배정이 아니라 분할 (`server/v4/inkOwner.ts`)

픽셀은 이미 나뉘어 있다(파트 마스크). 그러니 **추적 전에** 잉크를 파트별로 쪼갠다.
그러면 어떤 패스도 파트 경계를 넘지 않는다.

1. 파트 마스크를 z 오름차순으로 덮어써 픽셀마다 주인을 정한다(맨 앞 파트가 갖는다).
2. 어느 마스크에도 안 든 잉크는 **잉크 연결을 따라** BFS 로 주인을 물려받는다.
   유클리드 거리로 하면 선이 마스크 밖으로 삐져나간 곳에서 엉뚱한 파트가 잡힌다.
3. `strokeMask` · `outlineMask` · 검산 residual 을 주인별로 쪼개 **각각 추적**한다.
4. 이미 주인이 있는 기하는 `assignByCurve` 가 건드리지 않는다.

경계 픽셀은 맨 앞 파트가 갖고, 이웃도 그 선을 쓴다는 사실은 `shared` 로만 남긴다 —
잉크를 복제하지 않는다(복제하면 같은 선이 두 번 그려진다).

### 함께 고친 것 둘

- **폴리곤 크기 온전성.** Gemini 폴리곤이 대상의 일부만 훑고 끝나면 IoU 는 통과해도 그
  파트가 쪼그라든다 — bag_1 `top_handle` 폴리곤이 캔버스의 0.42% 뿐이라 손잡이 면이
  전부 이웃에게 넘어갔다(마스크 0.03%, precision 0.118). warp 는 경계는 못 믿어도
  **넓이**는 대체로 맞으므로, 폴리곤이 warp 면적의 절반도 안 되면 버린다.
  → top_handle 마스크 0.03% → **0.5%**, precision 0.118 → **0.635**.
- **면 귀속의 특정성.** 자격을 갖춘 후보 중 **마스크가 가장 작은** 파트가 갖는다.
  큰 마스크가 작은 파트를 감싸는 일이 흔하기 때문이다(베젤 마스크는 보석을 포함하고,
  플랩 마스크는 손잡이를 포함한다).

### 지표 결함 둘도 고쳤다

- **마스크가 없다시피 한 파트에 precision 을 적용하면 안 된다.** 기준이 조각뿐이라 제대로
  그린 기하도 전부 "밖"으로 세어진다. 0.2% 미만은 **판정 보류**로 이름과 함께 보고한다.
- **도면에 없는 파트**(마스크 0.05% 미만)는 벡터화 실패가 아니라 GPT 계획↔도면 불일치다.
  `absentInSchematic` 으로 따로 보고한다 — 섞어 세면 "레이어가 빠졌다"로 잘못 읽힌다.

### 주체탐지 플래그를 마스크 정합으로 교체했다

의미 gate 는 `correspondence.confident`(사진·도면에서 배경과 전경이 분리됐는가)를 보고
있었다. V4.3 부터 파트 경계는 도면의 닫힌 면에 스냅되므로 배경 분리 여부가 배분을 결정하지
않는다. **실측이 그것을 뒤집는다** — 그 플래그가 실패로 표시한 shoe_2·shoe_3 의 마스크
정합이 9종 중 가장 높다(0.964·0.982). 품질과 역상관이다.

대신 **마스크 정합**을 본다: 파트 마스크가 도면 잉크를 직접 덮은 비율(BFS 상속은 안 센다).
낮으면 마스크가 도면 위 엉뚱한 자리에 있다는 뜻이고 그때 배분은 추측이 된다. 하한 0.7 은

## V4.3 — Phase B 1단계: 도면을 직접 segment 한다

의미 gate 0/9 의 천장은 warp 된 사진 마스크였다(bag_1 사진↔도면 종횡비 19.8% 불일치).
V4.3 은 그 천장을 건드린다 — **도면 자체를 segment 한다** (`server/v4/segSchematic.ts`).

### 경로에 실측 근거가 있다

- **Gemini native segmentation 은 REST 로 못 쓴다.** mask 자리에 `<seg_N>` 특수 토큰이
  그대로 내려온다(서버측 후처리가 안 붙는다). → **폴리곤**으로 받는다.
- **`thinkingBudget: 0` 은 좌표 나열에서 무한 반복을 만든다**(MAX_TOKENS 실측).
  thinking 기본값 + temperature 0.6, 실패 시 온도를 올려 재시도.
- **설명만 주면 엉뚱한 영역을 잡는다**(front_flap 실측). warp 마스크의 bbox 를 위치
  힌트로 준다 — 대략 위치는 warp 가, 정밀 경계는 도면 쪽 모델이 맡는 역할 분담.
- **폴리곤(16~40점)은 경계가 선과 안 맞는다** — precision 은 오르고 recall 이 떨어졌다.
  → **면 스냅**: 도면에서 파트 경계는 반드시 그려진 선이므로, 선이 감싼 면(face)을 원자
  단위로 "폴리곤이 면의 40% 이상을 덮으면 면 전체 귀속". 겹치면 **z 최상위 파트** 소유 —
  트림 밴드가 플랩 위에 있으면 밴드 면은 밴드 것이다(argmax 로 하면 큰 폴리곤이 좁은
  파트의 면을 전부 빼앗는다. 실측: red_trim_bands recall 0.187 → 0.005 소멸 후 복구).
- **Gemini 와 warp 마스크를 절반씩 섞으면 안 된다.** 좌표 정합이 달라 이웃 파트끼리
  기준이 어긋난다(실측: bag_3 0.708 → 0.435). 채택률 80% 이상일 때만 통째로 쓰고
  아니면 전부 warp. **면 스냅은 출처와 무관하게 항상** — shoe_3 는 Gemini 2/8 뿐인데도
  스냅만으로 0.495 → 0.628 이 됐다.

## V4.2 — 외부 딥리서치 반영 (Phase A)

레이어 분리·점 밀도에 대한 두 번째 외부 분석을 받아 코드 실태와 대조 검증했다. 판정 전문과
단계별 계획은 [docs/plans/V42_METHOD.md](docs/plans/V42_METHOD.md). 요지:

- **채택** — layer-first + global-vector-once 하이브리드. 도면 좌표계 하나에서 semantic mask 를
  만들고 선은 한 번만 벡터화한다. 이미 그 구조이고, 부족한 것은 mask 의 품질이다.
- **기각** — 파트 crop 을 각각 이미지 모델로 다시 그려 합치는 방식. 공유 경계가 파트마다
  달리 그려져 이중선·틈이 생기고, 같은 가림을 crop 마다 다르게 복원한다.
- **다음 단계(Phase B)** — 사진 마스크를 warp 하지 말고 **도면 자체를 직접 segment**.
  bag_1 은 사진↔도면 종횡비가 19.8% 어긋나 warp 로는 절대 안 맞는다. Gemini 2.5 Flash
  polygon 제안 + SAM 3 정교화(FAL 키 대기) + 도면 선 snap.

이번에 적용한 것은 신규 API 없이 가능한 Phase A 세 가지다.

### 1. 삭제 직전 디테일 구제 (`server/v3/detailRescue.ts`)

해프톤 분류가 스티치 점선·로고 문자를 삼키던 것(V4.1 검증에서 발견)을 삭제 직전에 세 신호로
갈라 살린다 — **사슬 방향성**(신장률 ≥2.2 대시가 장축 방향으로 이어지고 간격 CV ≤0.45),
**크기**(해프톤 점 중앙값의 8배 이상), **구멍**(O·R·B 같은 문자).

첫 구현은 니트 코를 스티치로 오인했다 — 니트 코도 길쭉하고 줄지어 있다. shoe_3 에서
52사슬·9,667px 를 잘못 살려 선 F@2 가 1.000 → 0.922 로 무너졌다. **이웃 분포 검사**로
해결: 스티치 대시의 이웃은 사슬 방향 앞뒤 2개뿐이고, 직물 조직의 코는 전방향으로 촘촘하다
(길쭉한 이웃 5개 이상이면 2차원 조직으로 보고 거부).

결과: bag_1 에서 스티치 대시 37개 + 디테일 14개(7,831px)가 살아나 전체 잉크 F@2
0.895 → **0.912**. shoe_3 는 4대시(529px)만 구제되고 선 F@2 1.000 유지.

### 2. 닫힌 면도 패턴 후보로 (`pattern.ts` · `scene.ts`)

비즈 알·아웃솔 러그·보석 알은 독립된 잉크 성분이 아니라 **선이 감싼 면**이라 패턴 검출기가
영영 못 봤다. `findPatterns` 입력을 일반화하고(`PatternCandidate`), 면 군집 검사를
프리미티브 적합보다 **먼저** 돌린다. 인스턴스마다 파트를 따로 배정한다.

| | V4.1 | V4.2 |
|---|---:|---:|
| bag_3 패스 | 747 | **366 (−51%)** |
| shoe_3 패스 | 739 | **499 (−33%)** |

여기서도 함정이 하나 있었다: 면에서 온 패턴은 잉크가 아니다. QA 의 잉크 렌더에서
FACE_FILL 과 같은 규칙으로 제외하지 않으면 **흰 돌 내부가 검정 잉크로 세어져**
bag_3 F@2 가 1.000 → 0.867 로 무너진다(실측 후 `paint: "fill"` 표시로 수정 —
V4.1 의 GEOMETRIC_PRIMITIVE 렌더링 버그와 정확히 같은 계열이다).

### 3. 원본 좌표 기준 단순화 허용오차

허용오차 0.8px 가 2배 확대 작업 캔버스에 적용돼 실제로는 원본 기준 0.4px 로 재고 있었다.
`eps = min(1.6, simplifyPx × supersample)` 로 환산. 앵커 합계 123,248 → **114,890 (−6.8%)**,

## V4.1 — Semantic Topology Vectorizer

V3까지는 잉크 전체를 한 방식으로 훑고 SVG 하나를 만들었다. V4는 **성분마다 표현을 먼저 정하고**,
같은 장면(`VectorScene`)에서 목적별로 다른 SVG를 굽는다. `server/v4/`.

```bash
npx tsx server/run-v4.ts photo.jpg shoe_1 --category shoe
```

### 왜 파일이 셋인가

충실도와 편집성은 **반대 방향**이다. 충실도를 올리면 패스가 늘고, 패스를 줄이면 디테일이 깎인다.
V3는 그 둘을 한 파일에 동시에 요구해서 어느 쪽도 만족스럽지 않았다. V4는 파일이 아니라
**표현 단계**에서 가른다.

| 산출물 | 목적 |
|---|---|
| `fidelity.svg` | 도면과 최대한 같아 보이는 것. 앵커 예산 없음 |
| `editable.svg` | 적은 패스·앵커. 단순화 허용오차를 키우고 자잘한 조각을 버린다 |
| `production.svg` | 테크팩용. 기능 레이어(FILLS/OUTLINES/PRIMITIVES/STITCH/PATTERNS/SHARED_BOUNDARIES) + 파트 |
| `layered.ai` | Illustrator. 중첩 OCG → 기능 레이어 + 파트 하위 레이어 |
| `native-layers.jsx` | Illustrator ExtendScript. 실행하면 네이티브 레이어로 재구성된다 |
| `scene.json` | VectorScene 전문. 성분마다 **왜 그 표현을 골랐는지**가 문장으로 들어 있다 |

### 한 성분에는 한 표현만

V3의 `isStructural()`은 길이와 `length/width` 두 가지만 봤다. 주석에는 "폭이 안정적인"이라
써 놓고 폭의 안정성을 재지 않았고, 교차점도 보지 않았다. 그래서 굵기가 들쭉날쭉한 로고 덩어리나
교차가 잔뜩인 끈 뭉치도 길기만 하면 stroke로 승격됐다 — centerline이 가장 못하는 두 경우다.

V4는 성분마다 **폭 평균/중앙/표준편차/변동계수 · 골격 길이 · 끝점 · 분기 밀도 · 구멍 · 채움률 ·
프리미티브 적합 잔차**를 재고 아래 중 하나만 고른다.

| 분류 | 표현 | 조건 |
|---|---|---|
| `STRUCTURAL_STROKE` | centerline + stroke-width | 길이·길이/굵기·폭 변동계수·분기 밀도를 **모두** 만족 |
| `GEOMETRIC_PRIMITIVE` | 원·타원·직선·둥근사각 파라미터 | 적합 잔차가 max·rms 둘 다 임계 이하 |
| `REPEATING_PATTERN` | `<symbol>` 하나 + `<use>` 여럿 | 형상 편차가 작은 군집 20개 이상 |
| `DASH_OR_STITCH` | carrier 곡선 + `stroke-dasharray` | 일정 간격 · 직선성 2% 이내 |
| `OUTLINE_SHAPE` | 채워진 컴파운드 패스 | 위 조건 미달 (왜 미달인지 기록) |
| `FACE_FILL` / `TEXTURE_TONE` | 닫힌 면 · 해프톤 톤 | |

### Illustrator 파일 — 레이어가 실제로 나뉘어 온다

**SVG 는 Illustrator 에서 레이어가 오지 않는다.** 최상위 `<g>` 는 그냥 그룹이 되고 레이어 패널에는
`<Group>` 하나만 뜬다. 테크팩을 쓰는 사람은 레이어 패널에서 파트를 켜고 끄므로 그것으로는 일이 안 된다.
그래서 `layered.ai` 를 따로 굽는다 — .ai(PDF 호환)의 **중첩 OCG** 가 Illustrator 에서 레이어·하위
레이어로 복원된다.

```
FILLS               ← 기능 레이어
  └ Main upper      ← 파트 하위 레이어
  └ Laces
  └ Rubber outsole
OUTLINES
  └ Main upper
  …
PRIMITIVES / STITCH / PATTERNS / SHARED_BOUNDARIES
```

**레이어 순서는 기능이 먼저다.** 파트를 최상위로 두면 아래 파트의 선 위로 위 파트의 흰 면이 덮인다 —
면은 불투명하다. 보이는 그림이 달라지면 레이어 구조가 아무리 예뻐도 틀린 파일이다.
Illustrator 가 설치된 PC 를 위해 `native-layers.jsx` 도 함께 낸다(파일 > 스크립트로 실행하면
네이티브 레이어·그룹·패스로 재구성된다).

```bash
npx tsx server/v4/rebuild-exports.ts    # scene.json → svg 3종 + layered.ai + jsx
npx tsx server/v4/verify-ai.ts          # 레이어·그림·끊김 검증
npx tsx server/v4/break-map.ts jewelry_3 out.png   # 끊긴 곳을 눈으로
```

#### 세 가지를 각각 다른 방법으로 검증한다

| | 방법 | 결과 (9종) |
|---|---|---|
| 레이어 | .ai 를 되읽어 OCG 트리를 세운다 | 레이어 36 · 하위 141 · **레이어 밖 패스 0개** · 중첩 깊이 2 · BDC/EMC 짝 맞음 · 패스 합계가 장면과 정확히 일치 |
| 그림 | **제3의 렌더러(poppler)**로 .ai 를 굽고 SVG 래스터와 픽셀 비교 | 평균 IoU **0.970** (0.923~0.989). 남은 차이는 두 렌더러의 안티에일리어싱이고 양방향으로 고르게 난다 |
| 끊김 | 도면 선의 골격 중 .ai 가 못 덮은 구간을 성분으로 묶어, 양끝이 이어진 **끊김**과 이웃이 없는 **통째 누락**을 갈라 셈 | **제품 구조선에서 끊김 0곳.** 다만 누락은 0이 아니다 — 아래 절 참조 |

제3의 렌더러를 쓰는 이유는 우리 코드가 자기 자신을 채점하지 않게 하려는 것이다. 같은 라이브러리로
굽고 비교하면 좌표를 통째로 잘못 써도 IoU 1.0 이 나온다.

끊김은 숫자만 보고 판정하지 않는다. `break-map.ts` 가 도면 위에 못 덮은 구간을 빨갛게 칠해 주고,
9종을 눈으로 확인했다 — jewelry_3 의 673px 은 보석 세 개 **안쪽**이고, shoe_2 의 조각 1,188개는
메시 해프톤 점이다. 링 밴드·프롱·아웃솔·끈·시임·로고 같은 구조선은 이어져 있다.

#### 검증하다 더 큰 것이 나왔다 — 해프톤 분류가 스티치와 로고까지 삼킨다

끊김을 셀 때 **양끝이 이어진 "끊김"** 과 **이웃이 아예 없는 "통째 누락"** 을 갈라 세야 한다.
갈라 세지 않으면 "끊김 0곳"이 "다 그렸다"로 읽힌다.

| 샘플 | 선 중간 끊김 | 통째로 빠진 조각 | 해프톤 제외비 | 전체 잉크 F@2 | 제외 후 선 F@2 |
|---|---|---|---:|---:|---:|
| shoe_1 | 0 | 858곳 · 3,414px | 60% | 0.895 | 0.999 |
| shoe_2 | 3곳 · 11px | 1,143곳 · 2,910px | 44% | 0.908 | 0.999 |

| bag_1 | 0 | 1,297곳 · 3,668px | 62% | 0.895 | 0.998 |
| bag_2 | 0 | 17곳 · 33px | 0% | 0.937 | 0.937 |
| bag_3 | 0 | 0 | 0% | 1.000 | 1.000 |

**빠진 조각은 해프톤 제외비와 정확히 함께 움직인다.** 해프톤으로 분류된 영역은 점 하나하나를
패스로 만들지 않고 톤으로 치환하는데 — 그 자체는 옳은 결정이다, 안 그러면 편집이 불가능해진다 —
**그 분류가 너무 넓다.** bag_1 은 도면 잉크의 62%가 해프톤으로 잡히면서 옆면 메시 점무늬뿐 아니라
**스트랩 스티치 점선과 ORBITEC 로고 글자까지 함께 빠졌다.**

도면 위에 .ai 를 겹쳐 보면 바로 보인다(검정 = 둘 다, 빨강 = 도면에만, 파랑 = .ai 에만).
bag_1 은 외곽·패널 시임·핸들·버클이 전부 검정이고, 빨강은 스티치 점선·로고 글자·옆면 점무늬다.

그래서 **"선 F@2px 0.99x"는 이 4종에서 전체를 대표하지 않는다.** 62%를 빼고 잰 값이다.
전체 잉크 기준은 위 표의 왼쪽 숫자다. 이 절을 쓰기 전까지 앞의 README 와 데모는 제외 후 값을
앞세우고 있었다 — 그것을 고쳤다.

**다음에 고칠 것은 해프톤 판정이다.** 지금은 국소 점 밀도만 본다. 점선 스티치는 점이 규칙적으로
늘어서 있어 해프톤과 통계가 비슷하다. 방향성(스티치는 한 선을 따라 늘어선다)과 크기 분포를
같이 봐야 갈린다. 로고 글자는 획이 굵고 방향이 제각각이라 밀도만으로도 갈릴 수 있어야 한다.

#### 이 작업에서 실제 버그를 하나 잡았다

공유 경계 레이어는 맨 위에 그려지는데, 거기에 **불투명한 흰 면**이 올라가 그 아래 선을 지우고 있었다.
bag_3 은 공유 프리미티브 665개가 전부 `FACE_FILL` 이라 `production.svg` 의 잉크가 `fidelity.svg`
대비 **77%** 로 줄어 있었다 — **이미 배포돼 있던 파일이 다른 그림이었다**는 뜻이다.

| 샘플 | production/fidelity 잉크비 (수정 전) | .ai vs SVG IoU 수정 전 → 후 |
|---|---:|---|
| bag_3 | 0.771 | 0.747 → **0.952** |
| jewelry_2 | 0.937 | 0.914 → **0.978** |
| bag_2 | 0.960 | 0.890 → **0.923** |
| shoe_2 | 0.978 | 0.950 → **0.972** |
| shoe_3 | 0.992 | 0.964 → **0.977** |

`FACE_FILL` 과 `TEXTURE_TONE` 은 공유 경계 레이어로 올리지 않도록 `exportProduction()` 과
`sceneToAiDoc()` 양쪽을 고쳤다. 공유 여부는 `data-shared` 속성으로 그대로 남는다.

### 외부 감사에서 드러난 것 (V4.1)

V4를 배포한 뒤 외부 감사를 받았다. **가장 큰 것은 실제 렌더링 버그였다.**

닫힌 면에 적합한 기하 프리미티브를 `fill="none" stroke-width="0"` 으로 내보내
**화면에 아예 없었다.** 9종 합 329개 — bag_3 70/70, shoe_3 208/208, jewelry_1 1/1,
bag_1 3/3, shoe_1 21/26, shoe_2 15/23, jewelry_2 3/4. 구멍이 줄고 파트 recall이
떨어지던 원인이다.

| 고친 것 | 무엇이 틀렸나 |
|---|---|
| 프리미티브 칠하기 분리 | 선에서 온 것은 stroke, **면에서 온 것은 fill**. QA에 "굵기 0이면 invalid" 불변식 추가. 수정 후 9종 전부 0개, shoe_3 구멍 750→750으로 정확히 일치 |
| 면 배정 순서 | 화면 전체에서 색을 먼저 병합하니 서로 다른 부품의 흰 면이 한 패스가 되고, 그 패스가 결국 파트 하나에만 들어갔다. **파트 배정 → 같은 파트 안에서만 병합**으로 뒤집고, 배정을 경계 좌표 표본이 아니라 **면적 겹침**으로 바꿨다 |
| 의미 gate 재작성 | 평균 precision과 빈 파트 유무만 봤다. recall·IoU·대응 신뢰도를 안 봤고, 패스가 0인 파트는 평균에서 빠져 **큰 파트가 통째로 사라져도 점수가 올랐다** |
| 렌더러 통합 | QA가 패턴을 `d`로만 찾아 아예 못 그렸고, 기하 프리미티브를 전부 stroke로 그려 면을 놓쳤다. `renderPrimitive()` 하나를 export·QA가 함께 쓴다 |
| 편집성 지표 | `<path>` 요소만 세면 컴파운드 패스가 1개다. bag_3은 패스 747이지만 **서브패스 1,835, 한 패스에 1,089개**. 길이도 서브패스마다 따로 재야 존재하지 않는 도약이 안 더해진다 |

의미 gate의 새 조건:

```
correspondence.confident
  && 주요 파트(캔버스 2% 이상)가 전부 기준 통과
       면 파트: 자기 패스 > 0 && recall >= 0.55 && IoU >= 0.45
       선 파트: boundary F1 >= 0.80
  && 빈 파트 0
  && 배분 의심(precision < 0.5) 0
  && 면적 가중 평균 IoU >= 0.65
```

허용오차도 나눴다 — 면 0.1%, 선 0.6%. 예전엔 둘 다 캔버스의 1%(2,000px 캔버스에서 20px)라
이웃 파트의 선까지 들어와 precision이 과대평가됐다.

**그 결과 의미 gate는 9종 모두 REVIEW다.** 이전 5/9 PASS는 거짓이었다. 파트 레이어
ownership은 아직 신뢰할 수 없고, 이제 QA가 그것을 숨기지 않는다 — 기준 미달 파트를 이름으로
지목한다(예: bag_3 `chain_strap`, `inner_pouch`).

### 아직 남은 것 — 감사가 지적한 P1

- **라우팅 단위가 connected component라 너무 크다.** 제품 선화는 외곽·seam·끈·로고가 서로 닿아
  하나의 거대한 성분이 되므로 폭 변동과 교차가 커지고, 결국 전체가 outline으로 간다. 그래서
  9종에서 구조적 centerline이 거의 생성되지 않는다. junction을 축약한 **graph edge 단위**로
  라우팅해야 한다.
- **junction continuity를 전역으로 풀지 않는다.** 체인을 독립적으로 피팅하므로 같은 교차점에서
  시작한 두 곡선이 미세하게 다른 좌표로 끝날 수 있다.
- **가변 폭이 없다.** stroke 굵기가 체인당 상수 하나다.
- **곡선 스티치를 못 잡는다.** 직선성 2% 이내만 dash로 승격한다.
- **패턴 인스턴스 회전이 0 고정이다.** 서술자는 회전 불변이라 군집은 잘 찾지만, 배치할 때 각도를
  복원하지 않는다.

### 임계는 손실을 재고 정했다

이 부분이 V4에서 가장 오래 걸린 일이다. 처음 값들은 전부 헐거웠고, 압축률만 보면 좋아 보였다.

- **프리미티브** — 최대 잔차만 보면 안 된다. 대부분 어긋나는데 한 점만 우연히 가까운 적합도
  통과한다. 실측: 신발 도면에서 351개가 타원으로 승격돼 선 충실도가 0.996 → 0.962 로 떨어졌다.
  평균(rms)도 함께 보고 허용치를 캔버스 최소변의 0.4% → 0.25% 로 조였다.
- **패턴** — 형상 편차를 0.18까지 허용했더니 작은 성분 보존율이 1.00 → 0.75, 구멍이 317 → 271 로
  떨어졌다. **닮은 것과 같은 것은 다르다.** 0.05 로 조이니 신발은 압축이 0이 되고(원래 반복이
  아니었다) 비즈 메시 가방만 2,585패스를 줄였다.
- **점선** — 곧지 않으면 `dasharray` 로 바꿀 수 없다. 억지로 바꾸면 점이 제자리를 벗어난다
  (주얼리 도면 구멍 38 → 24). 직선성 2% 이내만 승격한다.
- **구조선** — stroke 가 그 잉크를 다 설명한다는 보장이 없다. 실제로 그려 보고 안 덮인 잉크만
  윤곽으로 보태는 **사후 검산**을 넣었다.

### 3-gate QA

V3는 PASS 하나로 모든 품질을 표현했다. 그래서 "원본과 똑같지만 패스가 3,583개"인 결과와
"패스는 적지만 디테일이 빠진" 결과를 같은 말로 불렀다. 둘은 다른 실패다.

| gate | 재는 것 |
|---|---|
| 충실도 | raw 도면 대비 F@0/1/2 · 선 굵기 비 · chamfer/p95 · 작은 디테일 보존율 · **구멍 수** · 큰 성분 수 |
| 편집성 | 패스·앵커·use·KB · **윤곽 100px당 앵커 밀도** · 짧은 패스 비율 · 프리미티브/패턴 절감 · editable 절감률 |
| 의미 | 파트별 실측 precision/recall/IoU · 공유 경계 수 · 빈 파트 · 종횡비 불일치 · 라우터 저확신 성분 |

상태는 세 관문의 조합으로 보고한다 — 예: `FIDELITY_PASS / EDITABILITY_PASS / SEMANTIC_REVIEW`.

### 아직 없는 것

기획서의 나머지는 **모델 가중치와 GPU가 필요해 붙이지 않았다.**

- **topology 엔진** (SLD · Deep Sketch Vectorization) — 교차점에서 어느 선이 어느 선의 연장인지
  전역으로 푸는 일. 지금은 여전히 체인을 독립적으로 피팅한다.
- **differentiable refinement** (Bézier · NURBS Splatting) — 제어점·폭을 렌더 손실로 최적화.
  가변 폭이 여기 딸려 온다. 지금 선 굵기는 체인당 중앙값 하나다.
- **dense correspondence** (DINOv3) — 사진↔도면의 조밀 대응. 지금은 등방 상사변환 하나뿐이라
  파트 배분이 근사다(실측 평균 precision 0.65~0.89).
- **appearance 분해** (COVec) — 금속 반사·그라데이션을 albedo/shade/highlight 로 나누는 일.
  jewelry_3 가 여기 걸린다.

`server/v4/` 는 그 자리에 어댑터 경계만 두고 현재 경로로 돈다.

사진을 먼저 **VRINGON schematic 워커**로 도면화하고, 그 **라인을 기준으로** 벡터를 만드는
세 번째 파이프라인입니다. `server/v3/`.

```bash

npx tsx server/run-v3.ts photo.jpg bag_1  --category bag --color            # 컬러 플랫
npx tsx server/run-v3.ts photo.jpg bag_1  --category bag --vector outline   # 최고 충실도
```

### 왜 도면을 먼저 만드는가

V1·V2는 **사진 위에서** 파트 경계를 찾습니다. 사진에는 그라데이션·그림자·질감이 있어
같은 파트가 명암 때문에 여러 조각으로 쪼개지고, 색이 비슷한 이웃 파트는 하나로 뭉칩니다.
도면화를 먼저 하면 그 문제가 사라집니다 — **도면의 선이 곧 파트 경계**입니다.
그리고 면과 선을 **같은 이진 마스크**에서 뽑으므로 경계가 정확히 맞물립니다.

### 8단계

| 단계 | 하는 일 |
|---|---|
| S1 | 정규화 · 배경 격리 · 크롭 |
| S2 | GPT-5.6이 구성품 분해 (id · 라벨 · bbox · z · occludedBy · kind) |
| S3 | 파트 마스크 (사진 좌표계) |
| S4–S5 | VRINGON 도면 생성 — **도면은 그대로 두고**, 파트 마스크를 등방 변환으로 도면 좌표계에 옮긴다 |
| S6 | **라인 기준 벡터화** — 잉크 마스크 → 바깥에서 flood fill → 닫힌 면은 fill, 선은 hybrid |
| S7 | 레이어 어셈블 (`<g id="layer-…">`) |
| S8 | **사용자가 보는 도면**과 대조하는 QA |

도면 생성은 사내 워커(`generate_schematic_image` @ qa)의 상수·순서를 그대로 옮겼습니다 —
1024×1024 stretch(bilinear) → `qwen-image-edit` + 공개 LoRA(strength 1.2, seed 484861632801927,
viewpoint 절 포함) → 종횡비 복원 → [컬러면] nano-banana 컬러화 → 업스케일.
상수는 `server/v3/schematicConstants.ts`에 원문 그대로 있습니다.
한 곳만 다릅니다 — **복원 단계에서 해상도를 모델 캔버스 아래로 내리지 않습니다**(아래 참조).
워커와 픽셀 단위로 같은 산출물이 필요하면 `matchWorkerResolution: true`로 되돌립니다.

### 선을 어떻게 표현할 것인가

| 모드 | 결과 | 강점 | 약점 |
|---|---|---|---|
| `centerline` | 열린 패스 + `stroke-width` | Illustrator에서 굵기·곡선을 바로 수정 | 교차점·가변 굵기·작은 디테일에서 무너짐 |
| `outline` | 채워진 컴파운드 패스 | 원본과 거의 구분 불가 | 선 하나가 리본이라 굵기 조절이 제한 |
| `hybrid` (기본) | 둘을 섞음 | 긴 구조선은 편집 가능, 나머지는 충실 | 패스 수가 중간 |

같은 도면을 정합 왜곡 없이 두 방식으로 떠서 잰 값:

| shoe_1 | F@2px | 작은 디테일 보존 |
|---|---:|---:|
| centerline | 0.869 | **0.045** |
| outline | 0.992 | 0.908 |
| outline 2배 | **0.9998** | 0.982 |

centerline이 스티치·지퍼 이빨·로고 문자를 통째로 잃는다는 것이 수치로 드러납니다.

### 외부 감사 후 고친 것 (2026-08-22)

외부 벡터화 품질 감사를 받고 파이프라인을 다시 만들었습니다. 지표의 기준을
**사용자가 화면에서 보는 도면**으로 바꾸자, 예전 QA가 통과시키던 결과가 실제로는
원본과 크게 어긋나 있었습니다.

> 9종 평균 — 예전 QA 보고 **0.872** · 왜곡된 내부 입력 대비 **0.917** ·
> **사용자가 보는 도면 대비 0.620**

원인은 하나가 아니라 여럿이었고, 전부 벡터화 **이전** 단계에 있었습니다.

**1. 도면을 사진 bbox에 욱여넣고 있었다.**
`alignToBox(..., { fit: "fill" })`이 x·y를 다른 배율로 늘렸습니다. 생성 도면은 사진을
**다시 그린 것**이라 종횡비가 애초에 다릅니다(bag_1 실측 21%). 손잡이 곡률·스트랩 폭·
버클 위치가 전부 바뀌었습니다.
→ **도면을 건드리지 않습니다.** 벡터는 도면 좌표계에서 만들고, 사진에서 온 파트 마스크
쪽을 등방 상사변환으로 옮깁니다. 남은 종횡비 불일치는 QA에 기록합니다.

**2. 배경 검출이 회색 배경을 전경으로 잡았다.**
`fgBBox`의 루미넌스 `<245` 규칙이 RGB 235짜리 도면 배경을 전경으로 판정해,
9종 중 **5종에서 bbox가 캔버스 전체**로 오판됐습니다(shoe_1·2·3, bag_1, bag_2).
→ 테두리에서 번지는 배경 flood fill로 바꿨습니다(`server/v3/subject.ts`).
검출에 실패하면 `confident: false`로 알리고 정합을 시도하지 않습니다.

**3. 모델이 1024²에 그린 획을 저장 직전에 버렸다.**
`schematicClient`가 원본 크기로 축소한 **뒤** 파일로 썼습니다. bag_1(304×433)은 모델
픽셀의 12.6%만 남았습니다. 같은 도면을 0.297배로 내려 벡터화하면 면 −86% · 노드 −77% ·
잉크 F1 −0.076입니다.
→ 종횡비만 되돌리고 해상도는 모델 캔버스 아래로 내리지 않습니다.

**4. 작은 성분을 승인 여부와 무관하게 전부 지웠다.**
해프톤 판정 코드가 클러스터 승인 검사를 해 놓고도 마지막에 모든 `speck`을 지웠습니다.
스티치·지퍼 이빨·로고 문자·짧은 접합선이 함께 사라졌습니다.
→ **승인된 질감 클러스터 안의 점만** 지웁니다. 그리고 질감이 잉크의 75% 이상을 차지하면
아예 지우지 않습니다 — 비즈 메시 가방처럼 질감이 곧 제품인 경우 톤 치환은 회색 덩어리만
남깁니다(실측 9종 질감 잉크점유: 0 / 0 / 0 / 0.005 / 0.257 / 0.443 / 0.601 / 0.652 / **0.810**).

**5. 전역 closing이 면과 선 양쪽에 걸렸다.**
닫힌 면을 찾으려면 외곽선에 1px 틈도 없어야 해서 closing이 필요합니다. 그런데 같은
마스크로 선까지 그리면 가까운 평행선이 붙고 교차점에 혹이 생깁니다(성분 11→7,
골격 끝점 57→27).
→ **면은 닫은 마스크로, 선은 원본 마스크로** 나눴습니다.

**6. 파트 배분이 베지어 제어점을 좌표로 썼다.**
`d` 문자열의 숫자를 정규식으로 훑었는데, `C x1 y1 x2 y2 x y`의 (x1,y1)·(x2,y2)는
**제어점**이라 곡선 위에 없습니다.
→ 명령을 실제로 해석해 arc-length에 가깝게 샘플링합니다(`server/v3/pathSample.ts`).
1·2위 파트의 점수가 비슷하면 공유 경계선으로 보고 `data-shared`에 남깁니다.

**7. QA가 자기가 망가뜨린 입력을 기준으로 삼았다.**
→ 기준을 raw 도면으로 바꾸고, 허용오차를 0/1/2px로 나눠 봅니다. 여기에 선 굵기 비,
대칭 chamfer와 p95, **작은 디테일 보존율**, 큰 성분 수, 종횡비 불일치, **파트별 실제 패스 수**를
더했습니다. 보이는 파트에 패스가 0개면 그것만으로 검토 대상입니다(예전에는 통과했습니다).

### 2차 — 선 굵기 상한 한 줄 (2026-08-22 저녁)

V4 기획 검토 중에 나온 것이다. **모든 구조선이 같은 굵기로, 그것도 실제보다 얇게 출고되고
있었다.** `server/vector/centerline.ts` 의 `chainWidth()` 안에 있던 `Math.min(6, …)` 는
centerline 이 원본 해상도에서 돌던 시절의 값인데, V3 는 도면을 2~4배로 키운 캔버스에서
추적하므로 실효 상한이 원본 기준 1.5~3px 이 됐다.

실측: **centerline 1,854개 중 1,745개(94.1%)가 정확히 6 에 붙어 있었다.** shoe_1 은 166개 중
162개, jewelry_1·2 는 전부였다. stroke 가 잉크를 덜 덮으니 남은 잉크(residual)를 outline 이
전부 떠맡아 패스가 폭증했다.

상한을 선/면을 가르는 기준(`min(W,H) × 0.012`, lineVector 의 `lineWidthLimit`)으로 바꿨다.
그보다 두꺼우면 애초에 선이 아니라 면이다. 중앙값을 쓰는 것은 그대로 뒀다 — p90 으로 바꾸면
교차부의 굵은 지점이 체인 전체를 부풀린다(실측 F@2px 0.9396 → 0.9090).

| 샘플 | 패스 | 노드 | 파일 | F@0px | 선 F@2px | 배분 precision |
|---|---|---|---|---|---|---:|
| shoe_1 | 890 → **423** | 15,098 → 9,545 | 684 → 427 KB | 0.789 → **0.831** | 0.998 → 0.994 | 0.853 |
| shoe_2 | 1,802 → **1,113** | 22,879 → 18,342 | 1,038 → 814 KB | 0.798 → **0.822** | 0.997 → 0.995 | 0.888 |
| shoe_3 | 2,728 → **1,549** | 42,423 → 28,966 | 1,894 → 1,280 KB | 0.869 → **0.902** | 0.998 → 0.996 | 0.849 |
| bag_1 | 406 → **224** | 6,662 → 4,929 | 285 → 207 KB | 0.794 → **0.816** | 0.999 → 0.997 | 0.745 |
| bag_2 | 3,583 → 3,537 | 36,312 → 36,161 | 1,616 → 1,608 KB | 0.664 → 0.669 | 0.945 → 0.946 | 0.650 |
| bag_3 | 1,636 → **1,342** | 18,374 → 17,362 | 841 → 782 KB | 0.891 → **0.901** | 0.999 → 0.997 | 0.707 |
| jewelry_1 | 235 → **82** | 5,034 → 2,391 | 223 → 104 KB | 0.891 → **0.927** | 0.991 → 0.986 | 0.803 |
| jewelry_2 | 542 → **172** | 5,112 → 2,910 | 235 → 132 KB | 0.857 → **0.910** | 0.994 → 0.997 | 0.821 |
| jewelry_3 | 467 → **296** | 4,708 → 3,731 | 210 → 164 KB | 0.743 → **0.774** | 0.867 → 0.870 | 0.775 |
| **합계·평균** | 12,289 → **8,738** (−29%) | 156,502 → **105,337** (−33%) | 7.03 → **5.52 MB** (−21%) | 0.811 → **0.839** | 0.976 → 0.975 | 0.788 |

패스 −29% · 노드 −33% · 용량 −21% 인데 **정확 일치(F@0px)는 오히려 올랐다**. 선 일치 F@2px 만
0.001 내려 사실상 동률이다. 8/9 PASS 는 그대로다.

bag_2 만 이득이 거의 없다(3,583 → 3,537). 잉크의 81%가 보존된 비즈 메시 질감이라 stroke 로
설명될 여지가 없다 — 그 패스 폭증은 반복 패턴 압축으로 풀어야 할 별개 문제다.

### 검증했지만 사실이 아니었던 것

V4 기획서는 hybrid 가 **"중앙 stroke + 양쪽 outline fringe 로 같은 선을 중복 표현한다"**고
지적했다. 실측으로 성립하지 않는다.

| | 겹침 `|C∩O|/|C|` | 순수 fringe | fringe 제거 시 F@2px |
|---|---:|---:|---|
| shoe_1 | 0.000 | outline 픽셀의 0.4% | 0.8944 → **0.8944** |
| bag_1 | 0.001 | 0.7% | 0.8981 → **0.8981** |
| jewelry_1 | 0.006 | 0.2% | 0.9910 → **0.9910** |

residual 을 `ink ∧ ¬dilate(covered, 1)` 로 정의하므로 두 마스크가 구조적으로 배타적이다 —
오히려 1px 간격이 강제로 벌어져 있다. 낭비되던 것은 잉크가 아니라 **객체 수**였고, 그 원인은
중복이 아니라 위의 굵기 상한 하나였다.

### 파트 배분은 이제 실제로 측정한다

`perPart.coverage` 가 전역 통계(`lv.stats.coverage`)의 복제였다. whole 경로에서는 모든 파트가
같은 `lv` 를 공유하므로 값이 전부 같게 나왔고(bag_1 8개 파트 전부 `0.9996`), 파트 배분이
맞는지는 아예 재지 않은 셈이었다.

이제 파트 레이어를 하나씩 따로 래스터화해 그 파트의 마스크(도면 좌표계로 옮긴 것)와
대조한다 — precision / recall / IoU. 선은 파트 경계에 놓이므로 마스크를 캔버스의 1% 만큼
넓혀서 재고, marking 류는 면을 안 채워 recall 이 구조적으로 낮으므로 **precision 만** 본다.
마스크가 없으면 `-1` 로 표시한다(전역값을 복제하지 않는다).

평균 배분 precision 은 0.65~0.89(전체 평균 0.788)다. 사진과 생성 도면은 원래 픽셀 정합되지
않으므로 1 이 될 수 없다. 다만 이제 그 오차를 숨기지 않고, precision 0.5 미만인 레이어를
이름으로 지목한다(실측: bag_1 `top_handle` 0.37, bag_2 `metal_frame`·`floral_ornament`).

파트 경계선은 소유자를 하나로 정하되 `data-shared` 로 이웃을 남긴다. 그리고 **여러 파트에
가려진 파트가 자기 패스를 못 가지는 것은 결함이 아니다** — 보이는 부분이 이웃과의 경계선뿐이고
그 선의 소유자는 앞쪽 파트이기 때문이다(bag_1 `main_compartment_shell` 은 4개에 가려져 있다).
QA 는 이것을 `sharedOnlyParts` 로 따로 세고 실패시키지 않는다.

### scope는 whole이어야 한다

schematic LoRA는 **제품 전체 사진**으로 학습돼 있습니다. 파트 크롭을 넣으면 분포 밖으로
나가서 그 조각을 단서로 완성품 하나를 지어냅니다 — 반지의 "검은 인레이" 크롭을 넣었더니
목걸이 펜던트가 나왔습니다.

| jewelry_1 | 실루엣 IoU | 선 일치 F | 사진 대비 IoU | 도면 생성 |
|---|---:|---:|---:|---:|
| `--scope part` | 0.889 | 0.468 | 0.327 | 191.0s |
| `--scope whole` | **0.958** | **0.925** | **0.881** | **13.3s** |

그래서 기본은 `whole`입니다. `part` 분기는 도면 모델을 파트로 파인튜닝할 때를 위해
남겨 뒀습니다.

### 컬러는 기하와 색을 나눠 뽑는다

컬러 도면은 선과 색면이 같은 검정이라 밝기 임계가 무너집니다 — 검정 가방에서 실측
패스 6개 · 실루엣 IoU 0.002. 컬러화는 모노 도면의 선을 그대로 보존하도록 프롬프트돼
있으므로, **컬러화 직전의 모노 도면에서 선을 뽑고 색만 컬러본에서 샘플링**합니다.

### 아직 남은 것

- **교차점(junction)을 전역으로 풀지 않습니다.** 어느 선이 어느 선의 자연스러운 연장인지
  판단하지 않고 체인을 독립적으로 피팅합니다. centerline 모드에서 분기점에 혹·틈이 남고,
  hybrid는 그 부분을 outline으로 돌려 가리고 있을 뿐입니다.
  (PolyVector·Deep Sketch Vectorization 계열이 다루는 문제입니다.)
- **선 굵기가 체인당 중앙값 하나**입니다. 원근으로 폭이 변하는 스트랩은 정확하지 않습니다.
- **파트 경계선을 공유 레이어로 빼지 않습니다.** `data-shared`로 표시만 합니다.
- **사진 파트 마스크와 생성 도면은 원래 정합되지 않습니다.** 등방 변환으로 옮기지만
  내부 경계는 근사입니다 — 종횡비 불일치를 QA에 기록합니다.
- **도면이 사진처럼 그라데이션으로 그려져 오면** 이진 추적의 한계에 걸립니다
  (jewelry_3: 보석이 사진 같은 명암으로 그려져 F@2px 0.867).

## V2 — 레이어 분리 벡터 SVG (개발계획서 구현)

`server/v2/`는 별도 설계 문서(*단일 객체 디자인 이미지의 레이어 분리 벡터 SVG 변환 시스템*, v1.0)를
그대로 구현한 **두 번째 파이프라인**입니다. V1과 목표가 다릅니다.

| | V1 (기본) | V2 (`server/v2/`) |
|---|---|---|
| 목표 | 테크팩용 **클린 플랫 도면** | **원본 충실 재현** (사진 픽셀 보존) |
| 경로 | 사진 → 플랫 스케치 생성 → 분해 → 벡터 | 사진 → Layer Manifest → 가시 마스크 → amodal 복원 → 벡터 |
| 산출 | `.ai` / `.jsx` / `.svg` / IR | `layered.svg` / manifest / layers/{id}.{png,svg} / QA / bundle |
| 강점 | 패스·노드가 적어 편집이 가볍다 | 형상·색이 원본과 일치한다 |

```bash
npx tsx server/run-v2.ts <이미지> <이름> --preset draft|standard|high --category jewelry.ring
npx tsx server/compare-v1-v2.ts            # 같은 지표로 V1↔V2 비교표
```

### 핵심 합성 규칙

생성 모델이 원본을 바꾸지 못하게, **보이는 픽셀은 원본에서 가져오고 가려진 부분만 생성**합니다.

```
M_hidden = clamp(M_amodal − dilate(M_visible, seam_margin), 0, 1)
RGB      = I_original × M_visible + G × M_hidden
Alpha    = union(M_visible, M_hidden)
```

**테크팩 용도면 V1, 원본 재현 용도면 V2**를 쓰세요.

### 모델 가용성

`Qwen-Image-Layered-Control`은 공개 inference provider가 없어 **자체 호스팅(80GB GPU)이 전제**입니다.
그래서 생성 워커를 두 백엔드로 만들었습니다.

- `QWEN_LC_URL` 설정 시 → 레이어별 프롬프트 추출 (설계 문서의 1순위 경로)
- 미설정 시 → 같은 계약을 채우는 대체 백엔드 (전체 분해 후 가시 마스크와 매칭)

두 경로 모두 후보마다 model revision·seed·config hash를 남기므로 GPU가 준비되면 env만 바꾸면 됩니다.
