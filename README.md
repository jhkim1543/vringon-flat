# VRINGON FLAT

**제품 사진 한 장 → 플랫 스케치 → 파트별 레이어 분리 → Illustrator `.ai` 자동 생성**

디자이너가 테크팩을 그릴 때 하는 일 — 사진을 평면 도식으로 옮기고, 파트마다 레이어를
나누고, 벡터로 다시 그리는 일 — 을 파이프라인으로 만든 것입니다.
결과물은 Illustrator에서 바로 열려서 파트별로 색·형태를 수정할 수 있습니다.

**▶ 데모 · 결과 9종 · V3 도면 기반 벡터 · V2 레이어 SVG · API 문서: https://jhkim1543.github.io/vringon-flat/**

<sub>신발 · 가방 · 주얼리를 중심으로 검증했고, 의류·안경·시계·가구 등 11개 카테고리와
분류 밖의 물건도 처리합니다.</sub>

## 빠르게 써 보기

```bash
git clone https://github.com/jhkim1543/vringon-flat
cd vringon-flat
npm install
cp .env.example .env      # OPENAI_API_KEY / GEMINI_API_KEY / FAL_KEY 입력
npm run dev:api           # → http://localhost:5201
```

브라우저에서 `http://localhost:5201/demo/` — 데모 화면이 그대로 뜨고, **직접 실행** 탭에서
내 이미지를 넣어 볼 수 있습니다. 웹 UI가 따로 필요하면 `npm run dev`(Vite 포함).

```bash
# API로 바로 쓰기
curl -X POST http://localhost:5201/v1/jobs -F "image=@sneaker.jpg" -F "categoryHint=footwear"
# → {"id":"…","statusUrl":"…","pollAfterMs":5000}

curl http://localhost:5201/v1/jobs/<id>          # status: running → done
curl -o result.ai http://localhost:5201/v1/jobs/<id>/file/ai
```

한 건에 **2~5분**이 걸립니다(생성 모델 2종 + 분해 + 벡터화). 그래서 동기 응답이 아니라
잡을 만들고 폴링하는 방식입니다.

## API

전체 명세는 [`docs/openapi.yaml`](docs/openapi.yaml) (OpenAPI 3.1)이고,
읽기 좋은 문서는 [데모 페이지의 API 탭](https://jhkim1543.github.io/vringon-flat/#api)에 있습니다.

| 엔드포인트 | 하는 일 |
|---|---|
| `POST /v1/jobs` | 이미지 업로드 → `202 {id}` (백그라운드 실행) |
| `GET /v1/jobs/{id}` | 진행률·단계·QA 지표·결과 파일 URL |
| `GET /v1/jobs/{id}/file/{ai\|svg\|jsx\|ir}` | 산출물 다운로드 |
| `GET /v1/jobs` | 최근 잡 목록 |
| `GET /v1/health` | 엔진·키·한도 (인증 불필요) |

**인증** — `.env`의 `API_KEYS`를 채우면 `X-API-Key` 헤더가 필수가 됩니다.
비워 두면 인증 없이 열립니다(로컬 개발 기본값). **공개 배포 시 반드시 설정하세요.**

**산출물 4종**

| 종류 | 내용 |
|---|---|
| `.ai` | PDF 호환 + OCG 레이어. Illustrator에서 바로 열림 |
| `.jsx` | Illustrator 스크립트. 실행하면 **네이티브 `.ai`** 생성 (레이어 패널 완전 지원) |
| `.svg` | 웹 미리보기·타 툴 반입 |
| `.ir.json` | Vector IR — 레이어→그룹→패스 구조를 코드로 다룰 때 |

`.ai`를 두 가지로 내보내는 이유: PDF-OCG 방식은 어디서나 열리지만 Illustrator의
레이어 패널과 완전히 같지는 않습니다. 네이티브 레이어가 필요하면 `.jsx`를 실행하세요.

## 파이프라인

```
0  입력 정규화 · 배경 격리 · 복수 객체 분리
1  이미지 이해        → Layer Plan (카테고리 · 파트 목록 · 그룹 구조)
2  플랫 스케치 생성    → 2개 모델 × (라인아트 · 컬러플랫)
3  후보 자동 평가      → 실루엣 IoU · 엣지 · 색 순도
4  amodal 레이어 분해  → 가려진 부분까지 복원한 파트별 레이어
5  재합성 QA · 자가교정 → 어긋난 곳을 그 자리에서 고침
6  레이어별 벡터화     → 면은 윤곽 추적, 선은 중심선 추출
7  패스 정리·검증      → 깨진 패스 제거, 앵커 과다 경고
8  .ai / .jsx / .svg / IR 생성
```

### 왜 사진을 바로 벡터화하지 않는가

사진에는 그림자·반사·직물 질감이 있고, 벡터화기는 그걸 전부 형상으로 봅니다.
메시 운동화 한 켤레가 8,000개가 넘는 패스가 됩니다.
플랫 스케치로 한 번 옮기면 **평면 색면 + 윤곽선**만 남아, 이후 단계가 다뤄야 할 대상이
분명해집니다. 면과 선을 같은 이미지에서 뽑기 때문에 선이 면과 어긋나지도 않습니다.

### 레이어 분해 — 도구를 각자 잘하는 범위에서만

| 도구 | 하는 일 | 한계 (실측) |
|---|---|---|
| amodal 분해 | 가려진 부분까지 복원한 재질 단위 레이어 | 파트 **이름을 모름**, 레이어끼리 겹침 |
| 색 클러스터 + 연결요소 | 같은 재질이 떨어져 있으면 별개 파트 | 색만 보면 토캡/힐카운터가 뭉침 |
| SAM 3 | 일반 명사 경계 보정 | `sole` `shoelace` `tongue`은 되지만 `vamp` `quarter`는 마스크 0개 |
| 비전 모델 + 규칙 | 조각에 파트 이름 배정 | 모델이 죽으면 규칙(위치·크기·색 사전)이 대신함 |

### QA가 파이프라인 안에 있다

레이어를 실제 색으로 다시 쌓아 플랫과 대조하고, 어긋난 곳을 **그 자리에서 고칩니다**:
덮이지 않은 전경 회수 · 색이 다른 덩어리 분리 · 이름 없는 잔재 정리.
최종 지표는 API 응답의 `qa` 필드로 나옵니다.

| 지표 | 뜻 | 통과 기준 |
|---|---|---|
| `coverage` | 전경 중 레이어가 덮은 비율 | ≥ 0.8 |
| `spill` | 배경을 침범한 비율 | ≤ 0.08 |
| `colorDeltaE` | 재합성 평균 색차 (0~441) | ≤ 60 |

**샘플 9종 실측** (전부 통과)

| 샘플 | 커버리지 | 배경 침범 | 색차 ΔE | 레이어 | 패스 |
|---|---:|---:|---:|---:|---:|
| shoe_1 | 99.7% | 1.0% | 6.7 | 13 | 278 |
| shoe_2 | 99.8% | 0.1% | 9.5 | 24 | 943 |
| shoe_3 | 100% | 0.3% | 6.5 | 16 | 412 |
| bag_1 | 100% | 0.9% | 10.9 | 14 | 109 |
| bag_2 | 99.5% | 1.0% | 2.1 | 10 | 91 |
| bag_3 | 99.2% | 0.4% | 14.0 | 9 | 1,099 |
| jewelry_1 | 99.8% | 0.2% | 4.3 | 12 | 116 |
| jewelry_2 | 96.0% | 0.4% | 10.0 | 25 | 251 |
| jewelry_3 | 88.4% | 0.0% | 18.2 | 22 | 263 |

## 임의의 이미지를 넣어도 되는가

0단계가 어떤 입력이든 파이프라인의 전제("흰 배경을 꽉 채운 제품 한 점")로 맞춥니다.

- EXIF 회전 · 알파 채널 · CMYK/16bit → sRGB · 애니메이션 첫 프레임
- 배경이 있으면 제품만 오려내고, 제품이 작게 찍혔으면 크롭 (화면 14% 점유일 때 색이 전부 어긋났음)
- 한 화면에 신발 2개·반지 3개가 있으면 **인스턴스별로 따로 처리**해 하나의 `.ai`로 합침
- 종횡비 6:1을 넘거나 손상된 파일은 `400`으로 거절

어느 단계가 실패해도 산출물은 나옵니다. amodal 분해가 비면 플랫 색분해로, 이름 배정이
실패하면 `Region N`으로, 한쪽 이미지 모델이 죽으면 다른 쪽으로 진행합니다.

```bash
docker build -t vringon-flat .
docker run -p 5201:5201 --env-file .env -v $PWD/outputs:/app/outputs vringon-flat
```

운영 시 확인할 것:

- `MAX_CONCURRENT_JOBS` — 외부 모델 비용·레이트리밋 때문에 기본 2. 초과 요청은 `429`

- 잡 목록은 **메모리에 있습니다**. 서버를 재시작하면 `GET /v1/jobs/{id}`는 404가 되지만
  산출물 파일은 디스크에 남습니다

## 개발

```bash
npm run dev          # API + 웹 UI
npm run typecheck
npm run smoke        # 과금 없는 스모크 테스트

npx tsx server/rebuild.ts <jobId>     # 생성 API 재호출 없이 분해~벡터화만 다시
npx tsx server/analyze.ts <jobId>     # 실루엣 IoU · 앵커 밀도 · 레이어 중복
npx tsx server/export-demo.ts         # docs/samples 갱신
npx tsx server/export-demo-v3.ts      # docs/samples-v3 갱신

npx tsx server/run-v3.ts <이미지> <이름> --category shoe   # V3 (도면 → 라인 벡터)
```

`rebuild.ts`는 이미 만들어진 잡의 플랫 이미지와 amodal 캐시를 재사용하므로
**재과금 없이** 분해·벡터화 로직을 반복 검증할 수 있습니다. 파이프라인을 고칠 때 이걸 씁니다.

벡터 뷰어: `http://localhost:5201/viewer?job=<8자리>` — 레이어 토글, 채움/외곽선/앵커 3뷰.

## 알려진 제약

- 파트 **이름**은 비전 모델이 없으면 위치·색 규칙으로만 붙어 거칩니다 (`Region N`이 남을 수 있음).
- 메시·비즈처럼 반복 질감이 많은 제품은 선 패스가 많아져 Illustrator가 무거워집니다.
- 한 장의 사진에서 보이지 않는 면(바닥·안감)은 만들 수 없습니다.
- 잡 목록이 메모리에 있어 서버 재시작 시 상태 조회가 끊깁니다(파일은 남음).

## V3 — VRINGON 플랫스케치 → 라인 기준 벡터화

사진을 먼저 **VRINGON schematic 워커**로 도면화하고, 그 **라인을 기준으로** 벡터를 만드는
세 번째 파이프라인입니다. `server/v3/`.

```bash
npx tsx server/run-v3.ts photo.jpg shoe_1 --category shoe
npx tsx server/run-v3.ts photo.jpg bag_1  --category bag --color            # 컬러 플랫
npx tsx server/run-v3.ts photo.jpg bag_1  --category bag --vector outline   # 최고 충실도
```

### 왜 도면을 먼저 만드는가

V1·V2는 **사진 위에서** 파트 경계를 찾습니다. 사진에는 그라데이션·그림자·질감이 있어
같은 파트가 명암 때문에 여러 조각으로 쪼개지고, 색이 비슷한 이웃 파트는 하나로 뭉칩니다.
도면화를 먼저 하면 그 문제가 사라집니다 — **도면의 선이 곧 파트 경계**입니다.
그리고 면과 선을 **같은 이진 마스크**에서 뽑으므로 경계가 정확히 맞물립니다.

### 8단계

| 단계 | 하는 일 |
|---|---|
| S1 | 정규화 · 배경 격리 · 크롭 |
| S2 | GPT-5.6이 구성품 분해 (id · 라벨 · bbox · z · occludedBy · kind) |
| S3 | 파트 마스크 (사진 좌표계) |
| S4–S5 | VRINGON 도면 생성 — **도면은 그대로 두고**, 파트 마스크를 등방 변환으로 도면 좌표계에 옮긴다 |
| S6 | **라인 기준 벡터화** — 잉크 마스크 → 바깥에서 flood fill → 닫힌 면은 fill, 선은 hybrid |
| S7 | 레이어 어셈블 (`<g id="layer-…">`) |
| S8 | **사용자가 보는 도면**과 대조하는 QA |

도면 생성은 사내 워커(`generate_schematic_image` @ qa)의 상수·순서를 그대로 옮겼습니다 —
1024×1024 stretch(bilinear) → `qwen-image-edit` + 공개 LoRA(strength 1.2, seed 484861632801927,
viewpoint 절 포함) → 종횡비 복원 → [컬러면] nano-banana 컬러화 → 업스케일.
상수는 `server/v3/schematicConstants.ts`에 원문 그대로 있습니다.
한 곳만 다릅니다 — **복원 단계에서 해상도를 모델 캔버스 아래로 내리지 않습니다**(아래 참조).
워커와 픽셀 단위로 같은 산출물이 필요하면 `matchWorkerResolution: true`로 되돌립니다.

### 선을 어떻게 표현할 것인가

| 모드 | 결과 | 강점 | 약점 |
|---|---|---|---|
| `centerline` | 열린 패스 + `stroke-width` | Illustrator에서 굵기·곡선을 바로 수정 | 교차점·가변 굵기·작은 디테일에서 무너짐 |
| `outline` | 채워진 컴파운드 패스 | 원본과 거의 구분 불가 | 선 하나가 리본이라 굵기 조절이 제한 |
| `hybrid` (기본) | 둘을 섞음 | 긴 구조선은 편집 가능, 나머지는 충실 | 패스 수가 중간 |

같은 도면을 정합 왜곡 없이 두 방식으로 떠서 잰 값:

| shoe_1 | F@2px | 작은 디테일 보존 |
|---|---:|---:|
| centerline | 0.869 | **0.045** |
| outline | 0.992 | 0.908 |
| outline 2배 | **0.9998** | 0.982 |

centerline이 스티치·지퍼 이빨·로고 문자를 통째로 잃는다는 것이 수치로 드러납니다.

### 외부 감사 후 고친 것 (2026-08-22)

외부 벡터화 품질 감사를 받고 파이프라인을 다시 만들었습니다. 지표의 기준을
**사용자가 화면에서 보는 도면**으로 바꾸자, 예전 QA가 통과시키던 결과가 실제로는
원본과 크게 어긋나 있었습니다.

> 9종 평균 — 예전 QA 보고 **0.872** · 왜곡된 내부 입력 대비 **0.917** ·
> **사용자가 보는 도면 대비 0.620**

원인은 하나가 아니라 여럿이었고, 전부 벡터화 **이전** 단계에 있었습니다.

**1. 도면을 사진 bbox에 욱여넣고 있었다.**
`alignToBox(..., { fit: "fill" })`이 x·y를 다른 배율로 늘렸습니다. 생성 도면은 사진을
**다시 그린 것**이라 종횡비가 애초에 다릅니다(bag_1 실측 21%). 손잡이 곡률·스트랩 폭·
버클 위치가 전부 바뀌었습니다.
→ **도면을 건드리지 않습니다.** 벡터는 도면 좌표계에서 만들고, 사진에서 온 파트 마스크
쪽을 등방 상사변환으로 옮깁니다. 남은 종횡비 불일치는 QA에 기록합니다.

**2. 배경 검출이 회색 배경을 전경으로 잡았다.**
`fgBBox`의 루미넌스 `<245` 규칙이 RGB 235짜리 도면 배경을 전경으로 판정해,
9종 중 **5종에서 bbox가 캔버스 전체**로 오판됐습니다(shoe_1·2·3, bag_1, bag_2).
→ 테두리에서 번지는 배경 flood fill로 바꿨습니다(`server/v3/subject.ts`).
검출에 실패하면 `confident: false`로 알리고 정합을 시도하지 않습니다.

**3. 모델이 1024²에 그린 획을 저장 직전에 버렸다.**
`schematicClient`가 원본 크기로 축소한 **뒤** 파일로 썼습니다. bag_1(304×433)은 모델
픽셀의 12.6%만 남았습니다. 같은 도면을 0.297배로 내려 벡터화하면 면 −86% · 노드 −77% ·
잉크 F1 −0.076입니다.
→ 종횡비만 되돌리고 해상도는 모델 캔버스 아래로 내리지 않습니다.

**4. 작은 성분을 승인 여부와 무관하게 전부 지웠다.**
해프톤 판정 코드가 클러스터 승인 검사를 해 놓고도 마지막에 모든 `speck`을 지웠습니다.
스티치·지퍼 이빨·로고 문자·짧은 접합선이 함께 사라졌습니다.
→ **승인된 질감 클러스터 안의 점만** 지웁니다. 그리고 질감이 잉크의 75% 이상을 차지하면
아예 지우지 않습니다 — 비즈 메시 가방처럼 질감이 곧 제품인 경우 톤 치환은 회색 덩어리만
남깁니다(실측 9종 질감 잉크점유: 0 / 0 / 0 / 0.005 / 0.257 / 0.443 / 0.601 / 0.652 / **0.810**).

**5. 전역 closing이 면과 선 양쪽에 걸렸다.**
닫힌 면을 찾으려면 외곽선에 1px 틈도 없어야 해서 closing이 필요합니다. 그런데 같은
마스크로 선까지 그리면 가까운 평행선이 붙고 교차점에 혹이 생깁니다(성분 11→7,
골격 끝점 57→27).
→ **면은 닫은 마스크로, 선은 원본 마스크로** 나눴습니다.

**6. 파트 배분이 베지어 제어점을 좌표로 썼다.**
`d` 문자열의 숫자를 정규식으로 훑었는데, `C x1 y1 x2 y2 x y`의 (x1,y1)·(x2,y2)는
**제어점**이라 곡선 위에 없습니다.
→ 명령을 실제로 해석해 arc-length에 가깝게 샘플링합니다(`server/v3/pathSample.ts`).
1·2위 파트의 점수가 비슷하면 공유 경계선으로 보고 `data-shared`에 남깁니다.

**7. QA가 자기가 망가뜨린 입력을 기준으로 삼았다.**
→ 기준을 raw 도면으로 바꾸고, 허용오차를 0/1/2px로 나눠 봅니다. 여기에 선 굵기 비,
대칭 chamfer와 p95, **작은 디테일 보존율**, 큰 성분 수, 종횡비 불일치, **파트별 실제 패스 수**를
더했습니다. 보이는 파트에 패스가 0개면 그것만으로 검토 대상입니다(예전에는 통과했습니다).

### 2차 — 선 굵기 상한 한 줄 (2026-08-22 저녁)

V4 기획 검토 중에 나온 것이다. **모든 구조선이 같은 굵기로, 그것도 실제보다 얇게 출고되고
있었다.** `server/vector/centerline.ts` 의 `chainWidth()` 안에 있던 `Math.min(6, …)` 는
centerline 이 원본 해상도에서 돌던 시절의 값인데, V3 는 도면을 2~4배로 키운 캔버스에서
추적하므로 실효 상한이 원본 기준 1.5~3px 이 됐다.

실측: **centerline 1,854개 중 1,745개(94.1%)가 정확히 6 에 붙어 있었다.** shoe_1 은 166개 중
162개, jewelry_1·2 는 전부였다. stroke 가 잉크를 덜 덮으니 남은 잉크(residual)를 outline 이
전부 떠맡아 패스가 폭증했다.

상한을 선/면을 가르는 기준(`min(W,H) × 0.012`, lineVector 의 `lineWidthLimit`)으로 바꿨다.
그보다 두꺼우면 애초에 선이 아니라 면이다. 중앙값을 쓰는 것은 그대로 뒀다 — p90 으로 바꾸면
교차부의 굵은 지점이 체인 전체를 부풀린다(실측 F@2px 0.9396 → 0.9090).

패스 −29% · 노드 −33% · 용량 −21% 인데 **정확 일치(F@0px)는 오히려 올랐다**. 선 일치 F@2px 만

bag_2 만 이득이 거의 없다(3,583 → 3,537). 잉크의 81%가 보존된 비즈 메시 질감이라 stroke 로
설명될 여지가 없다 — 그 패스 폭증은 반복 패턴 압축으로 풀어야 할 별개 문제다.

### 검증했지만 사실이 아니었던 것

V4 기획서는 hybrid 가 **"중앙 stroke + 양쪽 outline fringe 로 같은 선을 중복 표현한다"**고
지적했다. 실측으로 성립하지 않는다.

| | 겹침 `|C∩O|/|C|` | 순수 fringe | fringe 제거 시 F@2px |
|---|---:|---:|---|
| shoe_1 | 0.000 | outline 픽셀의 0.4% | 0.8944 → **0.8944** |
| bag_1 | 0.001 | 0.7% | 0.8981 → **0.8981** |
| jewelry_1 | 0.006 | 0.2% | 0.9910 → **0.9910** |

residual 을 `ink ∧ ¬dilate(covered, 1)` 로 정의하므로 두 마스크가 구조적으로 배타적이다 —
오히려 1px 간격이 강제로 벌어져 있다. 낭비되던 것은 잉크가 아니라 **객체 수**였고, 그 원인은
중복이 아니라 위의 굵기 상한 하나였다.

### 파트 배분은 이제 실제로 측정한다

`perPart.coverage` 가 전역 통계(`lv.stats.coverage`)의 복제였다. whole 경로에서는 모든 파트가
같은 `lv` 를 공유하므로 값이 전부 같게 나왔고(bag_1 8개 파트 전부 `0.9996`), 파트 배분이
맞는지는 아예 재지 않은 셈이었다.

이제 파트 레이어를 하나씩 따로 래스터화해 그 파트의 마스크(도면 좌표계로 옮긴 것)와
대조한다 — precision / recall / IoU. 선은 파트 경계에 놓이므로 마스크를 캔버스의 1% 만큼
넓혀서 재고, marking 류는 면을 안 채워 recall 이 구조적으로 낮으므로 **precision 만** 본다.
마스크가 없으면 `-1` 로 표시한다(전역값을 복제하지 않는다).

평균 배분 precision 은 0.65~0.89(전체 평균 0.788)다. 사진과 생성 도면은 원래 픽셀 정합되지
않으므로 1 이 될 수 없다. 다만 이제 그 오차를 숨기지 않고, precision 0.5 미만인 레이어를
이름으로 지목한다(실측: bag_1 `top_handle` 0.37, bag_2 `metal_frame`·`floral_ornament`).

파트 경계선은 소유자를 하나로 정하되 `data-shared` 로 이웃을 남긴다. 그리고 **여러 파트에
가려진 파트가 자기 패스를 못 가지는 것은 결함이 아니다** — 보이는 부분이 이웃과의 경계선뿐이고
그 선의 소유자는 앞쪽 파트이기 때문이다(bag_1 `main_compartment_shell` 은 4개에 가려져 있다).
QA 는 이것을 `sharedOnlyParts` 로 따로 세고 실패시키지 않는다.

### scope는 whole이어야 한다

schematic LoRA는 **제품 전체 사진**으로 학습돼 있습니다. 파트 크롭을 넣으면 분포 밖으로
나가서 그 조각을 단서로 완성품 하나를 지어냅니다 — 반지의 "검은 인레이" 크롭을 넣었더니
목걸이 펜던트가 나왔습니다.

| jewelry_1 | 실루엣 IoU | 선 일치 F | 사진 대비 IoU | 도면 생성 |
|---|---:|---:|---:|---:|
| `--scope part` | 0.889 | 0.468 | 0.327 | 191.0s |
| `--scope whole` | **0.958** | **0.925** | **0.881** | **13.3s** |

그래서 기본은 `whole`입니다. `part` 분기는 도면 모델을 파트로 파인튜닝할 때를 위해
남겨 뒀습니다.

### 컬러는 기하와 색을 나눠 뽑는다

컬러 도면은 선과 색면이 같은 검정이라 밝기 임계가 무너집니다 — 검정 가방에서 실측
패스 6개 · 실루엣 IoU 0.002. 컬러화는 모노 도면의 선을 그대로 보존하도록 프롬프트돼
있으므로, **컬러화 직전의 모노 도면에서 선을 뽑고 색만 컬러본에서 샘플링**합니다.

### 아직 남은 것

- **교차점(junction)을 전역으로 풀지 않습니다.** 어느 선이 어느 선의 자연스러운 연장인지
  판단하지 않고 체인을 독립적으로 피팅합니다. centerline 모드에서 분기점에 혹·틈이 남고,
  hybrid는 그 부분을 outline으로 돌려 가리고 있을 뿐입니다.
  (PolyVector·Deep Sketch Vectorization 계열이 다루는 문제입니다.)
- **선 굵기가 체인당 중앙값 하나**입니다. 원근으로 폭이 변하는 스트랩은 정확하지 않습니다.
- **파트 경계선을 공유 레이어로 빼지 않습니다.** `data-shared`로 표시만 합니다.
- **사진 파트 마스크와 생성 도면은 원래 정합되지 않습니다.** 등방 변환으로 옮기지만
  내부 경계는 근사입니다 — 종횡비 불일치를 QA에 기록합니다.
- **도면이 사진처럼 그라데이션으로 그려져 오면** 이진 추적의 한계에 걸립니다
  (jewelry_3: 보석이 사진 같은 명암으로 그려져 F@2px 0.867).

## V2 — 레이어 분리 벡터 SVG (개발계획서 구현)

`server/v2/`는 별도 설계 문서(*단일 객체 디자인 이미지의 레이어 분리 벡터 SVG 변환 시스템*, v1.0)를
그대로 구현한 **두 번째 파이프라인**입니다. V1과 목표가 다릅니다.

| | V1 (기본) | V2 (`server/v2/`) |
|---|---|---|
| 목표 | 테크팩용 **클린 플랫 도면** | **원본 충실 재현** (사진 픽셀 보존) |
| 경로 | 사진 → 플랫 스케치 생성 → 분해 → 벡터 | 사진 → Layer Manifest → 가시 마스크 → amodal 복원 → 벡터 |
| 산출 | `.ai` / `.jsx` / `.svg` / IR | `layered.svg` / manifest / layers/{id}.{png,svg} / QA / bundle |
| 강점 | 패스·노드가 적어 편집이 가볍다 | 형상·색이 원본과 일치한다 |

```bash
npx tsx server/run-v2.ts <이미지> <이름> --preset draft|standard|high --category jewelry.ring
npx tsx server/compare-v1-v2.ts            # 같은 지표로 V1↔V2 비교표
```

### 핵심 합성 규칙

생성 모델이 원본을 바꾸지 못하게, **보이는 픽셀은 원본에서 가져오고 가려진 부분만 생성**합니다.

```
M_hidden = clamp(M_amodal − dilate(M_visible, seam_margin), 0, 1)
RGB      = I_original × M_visible + G × M_hidden
Alpha    = union(M_visible, M_hidden)
```

**테크팩 용도면 V1, 원본 재현 용도면 V2**를 쓰세요.

### 모델 가용성

`Qwen-Image-Layered-Control`은 공개 inference provider가 없어 **자체 호스팅(80GB GPU)이 전제**입니다.
그래서 생성 워커를 두 백엔드로 만들었습니다.

- `QWEN_LC_URL` 설정 시 → 레이어별 프롬프트 추출 (설계 문서의 1순위 경로)
- 미설정 시 → 같은 계약을 채우는 대체 백엔드 (전체 분해 후 가시 마스크와 매칭)

두 경로 모두 후보마다 model revision·seed·config hash를 남기므로 GPU가 준비되면 env만 바꾸면 됩니다.
