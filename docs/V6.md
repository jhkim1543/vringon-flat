# V6.0 — 무엇을 고쳤고 무엇이 남았나

크롤링 26장(가방 11 · 신발 4 · 주얼리 11) 배치가 손으로 고른 샘플 9종이 못 보여 주던
결함을 드러냈다. V6.0 은 그중 **원인이 확정된 것만** 고친 판이다.

최종: 산출물 40개(면 모드 35 · 라인 모드 5) 기준 **충실도 40/40 · 편집성 40/40 · 의미 27/40**.
크롤링 26장의 게이트 통과는 55/78(71%) → 71/78(91%).
`.ai` 구조는 40개 전부 건전하다 — 트리 밖 OCG 0개, 하위 레이어 밖 페인트 0회, BDC/EMC 짝
맞음. 제3자 렌더러(poppler)로 구운 `.ai` 와 SVG 의 IoU 는 중앙 0.974.

## 1. 검게 채운 면이 통째로 사라지던 문제 — 가장 큰 결함

`evidence.ts` 는 선 굵기보다 두꺼운 잉크를 "선이 아니라 면"으로 갈라낸다. 갈라내는
판단은 옳다 — 면의 윤곽을 선 피팅에 넘기면 안쪽·바깥쪽에 앵커가 두 줄로 생긴다.

문제는 **갈라낸 것을 지역 변수에 담고 버렸다**는 점이다. 그래서 도면의 검은 면이
최종 산출물에서 증발했다.

| 실측 | 전 | 후 |
| --- | --- | --- |
| t_footwear_02 (검은 갑피 + 체커보드) F@0 | 0.765 | **0.953** |
| 〃 선 F@2px | 0.823 | **0.997** |
| 〃 chamfer | 3.84 | **0.06** |
| t_jewelry_03 (오팔 인레이) F@0 | 0.664 | **0.960** |

이제 `EvidenceField.solidFill` 로 장면 조립까지 넘어가고, 짙은 `FACE_FILL` 로 출고된다.
라인 모드에서는 면을 만들지 않기로 했으므로 윤곽만 선으로 남긴다.

## 2. 채점이 "있는 것을 그린 것"을 벌하던 문제

도면의 잉크 기준은 그레이 160 미만이다. 그런데 도면은 질감을 **그레이 200쯤의 옅은
회색 선**으로 그린다(실측 t_bag_09 크로커다일 무늬: 176~207). 한 기준으로 재현율과
정밀도를 다 재면, 그 무늬를 옳게 잡아낸 벡터가 "없는 것을 지어냈다"로 깎인다.

재현율과 정밀도는 묻는 것이 다르므로 기준선을 나눴다.

- **재현율** — "도면의 진한 선을 다 그렸나" → 그레이 < 160
- **정밀도** — "빈 종이에 없는 것을 그렸나" → 그레이 < 215

기준을 통째로 215 로 올리면 종이 얼룩과 안티에일리어싱까지 선이 되므로 그건 안 된다.

## 3. 앵커 병합을 전역 최적으로

기존 `thinAnchors` 는 왼쪽부터 되는 대로 합치는 탐욕이라, 한 번 잘못 합치면 그 뒤로
합칠 기회를 잃었다. Potrace 2.4 의 사상대로 "조각 i..j 를 큐빅 하나로 바꿀 수 있나"를
모두 재 놓고 **(조각 수, 오차 합) 사전식 최단경로**로 푼다.

닫힌 곡선의 이음매도 옮겼다. 이음매는 어떤 알고리즘도 넘어서 병합하지 못하는 자리라,
매끄러운 곡선 한복판에 있으면 앵커 하나를 그냥 버린다 — 가장 많이 꺾인 자리로 돌린다.

**같은 허용오차에서 −16.5%** (실측 t_bag_05: `.ai` 실앵커 27,784 → 23,186, 충실도 통과
유지). `V4_DP_LIMIT=0` 으로 탐욕으로 되돌려 같은 도면·같은 코드로 잰 값이다.

계수기를 섞지 말 것. QA 의 `editability.anchors` 와 `anchor-audit` 의 `.ai` 실앵커는
**다른 것을 센다** — 패턴을 인스턴스마다 펼치느냐가 다르다. 둘을 섞어 비교하면 없는
개선이 보인다(실제로 이번에 −28% 로 잘못 읽었다). 판 사이 비교는 항상 같은 계수기로.

## 4. 표본 한 개로 게이트가 갈리던 문제

"작은 디테일 60% — 2개 소실"은 작은 성분이 셋뿐인 도면에서 나온 수치다. 하나를
놓치면 67% 다. 그건 품질이 아니라 잡음이므로, 표본 8개 미만이면 수치는 보고하되
판정에서 뺀다.

## 5. 판정 사전을 하나로

`gemFlatten` 의 3차 패스에만 짧은 정규식(`gem|stone|diamond|crystal|pearl`)이 따로
있어서, `GEM_WORDS` 에는 있는 `opal`·`turquoise`·`sapphire` 가 그 패스를 건너뛰었다.
같은 판단을 두 군데에 적으면 언젠가 갈라진다.

같은 이유로 **"이 프리미티브가 잉크인가"** 판정도 `export.ts` 의 `isInkPrimitive`
하나로 모았다. 진단 도구가 자기만의 필터를 들고 있다가 면까지 검정으로 그려서,
멀쩡한 결과가 통짜 덩어리로 보이는 일이 실제로 있었다.

## 6. 모든 bbox 가 캔버스 전체였던 문제 — 가장 오래 숨어 있던 것

```js
const n = (d.match(new RegExp("-?\d*\.?\d+", "g")) ?? []).map(Number);
```

문법 오류가 아니다. JS 문자열 리터럴이 `\d` 를 `d` 로 삼켜 `/-?d*.?d+/` 가 되고, 패스
문자열에서 **매치가 0건**이라 `bboxOfPath` 가 조용히 기본값 `[0, 0, W, H]` 를 냈다.
예외도 안 나고 화면도 멀쩡해서 며칠을 살아남았다. 실제 피해는 둘이다.

- **연속성 구제가 통째로 꺼졌다.** `continuity.ts` 는 프리미티브 발자국을 재주입에서
  빼는데, bbox 가 캔버스 전체면 **모든 자리가 제외**된다. 끊긴 선이 하나도 안 구제됐다.
- **라인 모드 골격 점수가 0 이 됐다.** 글리프 영역을 골격 비교에서 빼는데, 글리프 10개의
  bbox 가 전부 캔버스 전체라 비교 영역이 남지 않았다(실측 jewelry_1_line: F@3 = 0).

고친 뒤 라인 모드 3종의 충실도가 X → O 로 돌아왔다.

재발 방지로 `scripts/check-regex-escapes.mjs` 를 넣었다 — `new RegExp("…")` 안에서
`\d`·`\w`·`\s`·`\b` 가 홀수 개 백슬래시로 적힌 곳을 찾아 종료 코드 1 을 낸다. **정규식은
리터럴 `/…/` 로 쓴다.**

## 남은 것 — 고치지 않았고, 고칠 계획도 없는 것

**질감이 촘촘한 제품의 앵커 수.** 코바늘·니트 가방은 1.5만~2.8만 앵커가 나온다
(보통 가방은 1,500~3,000). 실측 t_bag_05 는 OUTLINE_SHAPE 하나가 9,314 앵커인데,
그건 그물의 웹이 실제로 구멍 수천 개짜리 한 덩이이기 때문이다. 충실하게 그리는 한
줄일 수 없는 수이고, 편집성 게이트는 통과한다. 줄이려면 그물을 패턴으로 더 공격적으로
압축해야 하는데 그러면 실제 짜임이 사라진다 — **표현의 거래이지 결함이 아니다.**

**도면 자체의 문제.** "사진↔도면 종횡비 불일치", "도면에 없는 파트"는 도면 생성 단계가
사진과 다른 것을 그린 경우다. 벡터화가 고칠 수 있는 것이 아니라서 경고로만 남긴다.

## 검토했으나 채택하지 않은 것 (딥리서치)

- **Puhachov PolyVector Flow (2021)** — Gurobi 상용 라이선스 필요. 상업 파이프라인 부적격.
- **Virtual Sketching (2021)** — 실행마다 결과가 달라져 회귀 테스트가 불가능하고,
  SVG 변환 시 가변 폭이 소실된다(저자 명시).
- **LIVE (2022)** — 2K 이미지 한 장에 5시간. 채색 닫힌 path 모델이라 라인아트에 부적합.
- **DiffVG 직접 사용** — JS 바인딩 없음. 필요해지면 Bézier Splatting 을 사이드카로.
- **Steger 곡선구조 검출기** — 채택 가치가 가장 높은 미착수 항목. 이진화·세선화를
  건너뛰고 서브픽셀 중심선과 **선폭**을 동시에 낸다. 라인 모드의 폭 충실도를 고칠
  정공법이지만 400~600줄 규모라 이번 판에는 넣지 않았다.

## 7. V6.1 — 실무 심사가 바꾼 것

조사 자료를 근거로 만든 페르소나 20명(테크니컬 디자이너·풋웨어·핸드백·주얼리 CAD·
텍스타일·자수·스크린프린트·레이저·소싱 등)에게 원본 사진·도면·`.ai` 래스터·앵커 지도를
보이고 채점하게 했다. **이들은 실제 사람이 아니다** — 실사용자 조사가 아니라 직업적
관점을 구조화한 비평으로만 쓴다.

V6.0 결과: 편집성 4.2 · 실무투입가능성 4.0 · 기대충족 4.5 (10점 만점).
판정은 못 쓴다 12 · 손보면 쓴다 7 · 그대로 쓴다 1.

### 7-1. 치명적 지적 — 선이 확장된 면이었다

시니어 테크니컬 디자이너: *"선이 라이브 스트로크가 아닌 면(Fill)으로 확장됨 — 선 굵기
위계를 일괄 수정할 수 없어 파일 활용이 불가능"*. 프리랜서 일러스트레이터는 같은 것을
**이중선**이라 불렀다. 조사 자료가 "자동 트레이스의 최대 지문"으로 지목한 바로 그것이고,
실측으로 확인됐다 — 면 모드는 닫힌 서브패스의 15~22%가 선을 윤곽으로 뜬 것이다.

**그리고 이것이 앵커 과다의 원인이기도 하다.** 20명 중 16명이 앵커를 지적했는데, 선을
안·바깥 두 겹으로 뜨면 앵커가 두 줄이 되기 때문이다. 두 불만은 한 원인이다.

### 7-2. `lineMode` 를 두 축으로 갈랐다

`lineMode` 는 (가) 선을 중심선 스트로크로 내고 (나) 면을 아예 안 만드는 두 가지를 한꺼번에
했다. 심사에서 이 둘이 **서로 다른 사람의 요구**임이 드러났다.

- 테크니컬 디자이너·일러스트레이터·자수 디지타이저 → (가)가 필요
- 텍스타일·어패럴 그래픽 디자이너 → (나)는 곤란 ("면이 없어 색을 못 채운다")

그래서 `strokeLines` 를 따로 뒀다. `--stroke` 로 켜면 **면은 채울 수 있고 선은 굵기를
바꿀 수 있는** 산출물이 나온다 — 사람이 그린 도식화의 구조가 바로 그것이다.

| 실측 t_footwear_03 | 면 윤곽 | 라이브 스트로크 |
| --- | --- | --- |
| 앵커 | 1,943 | **1,176 (-39%)** |
| 이중선(닫힌 서브패스 중) | 15% | **0%** |
| 선 F@2px | 0.976 | **0.992** |
| 고유 선굵기 | 2개 | **4등급** |
| OUTLINE_SHAPE / STRUCTURAL_STROKE | 219 / 2 | **0 / 317** |
| FACE_FILL (채울 수 있는 면) | 83 | 72 |

### 7-2-1. **앵커 감소는 일반화되지 않았다 — 정정**

위 표는 t_footwear_03 **한 장**이다. 35장 배치로 재보니 그 이득은 일반적이지 않다.

| 35장 배치 | 면 윤곽 | 라이브 스트로크 |
| --- | --- | --- |
| 앵커 합계 | 116,538 | 118,681 (**+1.8%**) |
| F@0 평균 변화 | — | **-0.042** |

샘플별로 갈리는 폭이 크다 — jewelry_04 는 90% 줄었지만 jewelry_01·footwear_01 은
41~46% **늘었다**. 중심선은 체인마다 끝점 두 개가 붙기 때문에, 짧은 획이 많은 제품
(구슬 장식·각인 디테일)에서는 윤곽으로 길게 감싸는 쪽이 앵커가 적다.

**그래서 스트로크 모드의 값어치는 앵커 수가 아니다.** 실제로 유지되는 이득은 구조적인
것들이다.

| 실측 | 면 윤곽 | 라이브 스트로크 |
| --- | --- | --- |
| t_footwear_01 이중선(닫힌 서브패스) | 552개 중 66 (12%) | **55개 중 4 (7%)** |
| t_jewelry_01 〃 | 79개 중 13 (16%) | **0개 (0%)** |
| t_bag_10 〃 | 263개 중 57 (22%) | **30개 중 4 (13%)** |
| 선 굵기를 숫자로 일괄 변경 | 불가 (면으로 확장됨) | **가능** |
| 고유 선굵기 | 수십 개 | **2~4 등급** |

**거래도 있다.** F@0 가 평균 0.042 내려간다. 굵기를 등급으로 **재할당**하면 사진의 실제
굵기와는 멀어지기 때문이다. 조사 자료의 표현대로 "선 굵기는 재현이 아니라 재할당
문제"이고 실무 기준으로는 등급 쪽이 맞지만, 수치는 숨기지 않는다.

**한 장으로 일반화하지 말 것.** 이번에 실제로 저질렀다 — footwear_03 의 -39% 를 보고
"앵커가 39% 준다"고 적었는데, 배치로는 오히려 늘었다.

### 7-3. 선 굵기 등급화

실측 굵기를 그대로 쓰면 고유값이 수십 개로 흩어져 "같은 뜻의 선이 같은 굵기"가 깨진다.
길이로 가중한 1차원 k-means 로 등급 중심을 찾고 스냅한다(`refit.ts` `widthGrades`).
초기값은 가중 분위수다 — 무작위 초기화는 **실행마다 결과가 달라져** 쓸 수 없다.
조사 자료가 지적하듯 실무자는 결정성을 신뢰의 조건으로 본다.

### 7-3-1. 질감이 촘촘하면 중심선을 태우지 않는다

코바늘·니트의 그물에 중심선을 태우면 셀마다 골격 체인이 생겨 **추적이 사실상 멈춘다**
(실측 t_bag_05: 2시간 30분 뒤에도 안 끝남). 결과도 쓸모없다 — 디자이너가 원하는 것은
실 한 올마다 스트로크가 아니라 "여기가 짜임"이라는 표현이다.

**성분 수로는 못 가른다.** 그물은 연결된 한 덩이라 성분이 두엇뿐이다. 가르는 것은
**구멍 수**다.

| 도면 | 구멍 수 | 성분 수 |
| --- | ---: | ---: |
| 코바늘 가방 (bag_04·05·11) | 2,299 ~ 2,721 | 2 ~ 26 |
| 보통 제품 | 84 ~ 187 | 4 ~ 327 |

구멍 800개를 넘는 마스크만 윤곽 추적으로 보낸다. t_bag_05 가 **2시간 30분 → 1분 15초**
가 되고 세 게이트를 모두 통과한다.

### 7-4. 제품 밖 소품 제외

도면은 사진에 있는 것을 다 그린다 — 신발 안의 슈트리, 끈 끝 열쇠고리, 바닥에 놓인 선.
네 명이 같은 말을 했다. **판정은 크기가 아니라 거리로 한다** — 어느 파트 마스크에서도
멀리 떨어진 잉크 성분만 뺀다. 스트랩·체인처럼 마스크 밖으로 뻗는 부품은 제품에 닿아
있으므로 살아남는다. 크기로 가르면 그것들이 먼저 죽는다.

### 7-5. 판정 문턱을 플래그가 아니라 장면으로

"짧은 서브패스 47% — 파편화 의심"으로 중심선 산출물이 탈락했다. 닫힌 윤곽은 선 하나를
두 겹으로 떠서 서브패스가 길고, 중심선은 그 절반 길이의 열린 획이다 — 같은 그림인데
길이 척도가 다르다. 문턱을 **어떤 옵션으로 돌렸는지가 아니라 실제로 스트로크가 주인
장면인지**로 정하게 고쳤다.

### 7-6. 고치지 않기로 한 것 (요구가 상충한다)

- **레이어 최상위를 부품 단위로** (풋웨어 디자이너·패키징) ↔ **잉크 색상 단위로**
  (스크린프린트) ↔ 현재의 기능 단위. 하나로 정할 문제가 아니라 **프리셋** 문제다.
- **뒷면·인사이드 뷰** — 사진이 한 장뿐이면 만들 수 없다. 없는 것을 지어내는 쪽이 나쁘다.
- **정투상 3면도·mm 스케일** (주얼리 CAD) — 도면 생성 단계의 스펙이지 벡터화가 아니다.

## 8. V6.2 — 외부 코드 검토가 지적한 것

외부에서 소스와 산출물을 받아 검토한 결과를 반영했다. 지적은 **전부 사실이었다**.

### 8-1. 소스 묶음에서 25개 파일이 빠졌다 — 포장 결함

`continuity.ts` · `lineMerge.ts` · `letterDetect.ts` · `segSam3.ts` · `residualAssign.ts` 를
비롯해 **git 추적 안 되는 소스 25개**가 통째로 빠져 있었다. 최신 실행 경로가 import 하는
파일이라 **받는 쪽은 빌드조차 못 했다.**

원인은 담을 파일을 **이름으로 나열**한 것. 규칙을 뒤집었다 — `scripts/pack-source.sh` 는
소스 디렉터리를 통째로 담고 **빼야 할 것만 이름으로 뺀다.** 묶기 전에 두 가지를 검사하고,
하나라도 걸리면 묶지 않는다.

* 키로 보이는 문자열 (`sk-` · `AIza` · `r8_` · `hf_`)
* `server/v4/*.ts` 가 import 하는 모듈이 다 들어갔는지

### 8-2. 메인 실행이 `.ai` 를 안 냈다

`runV4()` 는 SVG 세 종류와 `scene.json` 만 썼고, `.ai` 는 `rebuild-exports.ts` 를 따로
돌려야 나왔다. README 의 실행 설명과 실제 동작이 어긋났고, **한 번만 돌린 사람은 정작
최종 산출물을 못 받았다.** 이제 `layered.ai` 와 `native-layers.jsx` 를 함께 낸다.

### 8-3. 곡선 QA 가 느슨했다

| 항목 | 전 | 후 |
| --- | --- | --- |
| 이탈 측정 방향 | 원본→곡선 **단방향** | **양방향** |
| 조각당 샘플 | 9점 고정 | 길이 비례 8~64점 |
| 허용 이탈 배수 | 8× | 4× |

단방향이면 곡선이 원본 **밖으로 부풀어도** 안 걸린다 — 원본 점마다 가까운 곡선점이 있기만
하면 통과하기 때문이다. 곡선 쪽에서 원본으로도 재야 그 부풂이 드러난다.

### 8-4. DP 가 진짜 전역이 아니었다

`if (err > tol) break` — 오차가 구간 길이에 **단조 증가**한다고 가정하고 탐색을 끊었다.
S 자로 굽은 구간은 반만 덮으면 한쪽으로 치우친 큐빅이 되지만, 굽이를 통째로 덮으면 대칭
큐빅 하나로 잘 맞는다. 끊으면 그 더 나은 해를 영영 못 본다. `continue` 로 바꿔 넘는
길이는 건너뛰고 계속 본다.

### 8-5. 절대 앵커 예산이 없었다

밀도만 보고 총량은 안 봤다. 그래서 앵커 2만 개짜리 파일이 밀도 5.6 으로 통과했다 —
디자이너가 여는 것은 밀도가 아니라 파일이고, 2만 앵커는 Illustrator 에서 줌·팬마다
버벅인다.

값은 실무 규범이 아니라 **관측된 분포**에서 잡았다: 보통 제품 1,500~4,000, 질감이 촘촘한
제품 1.8만~2.3만. 경고 8,000 · 탈락 20,000.

적용 결과 69건 중 `s_bag_05`(20,334) 하나가 편집성 탈락했다. **탈락시키는 것이 맞다** —
그 파일은 실제로 편집용으로 못 쓴다.

### 8-6. 재현성 정보가 부족했다

백엔드·프롬프트·시드만으로는 부족하다. 파이프라인 코드가 바뀌면 같은 도면에서도 다른
벡터가 나온다. `scene.provenance.run` 에 코드 판·실행 옵션·`V4_*` 환경변수·입력 해시를
남긴다. 나중에 "같은 사진인데 결과가 다르다"를 짚을 근거가 된다.

### 8-7. 지적 중 고치지 않은 것과 그 이유

* **`.ai` 가 네이티브 AI 가 아니라 PDF+OCG** — 사실이다. Illustrator 심볼·패턴 브러시·
  편집 가능 텍스트를 담으려면 JSX/플러그인으로 네이티브 객체를 재구성해야 한다.
  `native-layers.jsx` 를 함께 내보내지만 **Illustrator 를 띄워 실행해야** 하므로 무인
  파이프라인으로는 아직 못 넣는다.
* **패턴이 `.ai` 에서 인스턴스마다 펼쳐진다** — 사실이고, 앵커 절감의 가장 큰 미해결
  항목이다. PDF Form XObject 로 담아도 Illustrator 가 심볼로 복원한다는 보장이 없어
  검증 없이 바꾸면 더 나빠질 수 있다.
* **Steger 검출기 / 전역 선 그래프** — 방향은 옳다. 이번 판에서는 세선화를 유지한 채
  가지 치기와 상호 최선 짝짓기로 증상을 줄였다(끊김 40~42% → 17%).

## 9. v6.3 — 전체 회고 감사에서 새로 드러난 것

지금까지 지적된 것이 실제로 고쳐졌는지 **산출물에서 다시 재는** 감사 도구를 만들었다
(`server/v4/__audit.ts`). 문서에 "고쳤다"고 적힌 것을 믿지 않고, 항목마다 측정 방법과
함께 숫자를 찍는다. 그 감사가 **대화 중에는 못 본 결함 둘**을 잡았다.

### 9-1. `--line` 모드에 굵기 등급화가 안 걸렸다

`widthGrades` 를 `--stroke` 에만 걸어 두었다. 그런데 `--line` 도 스트로크를 낸다 —
그래서 라인 모드는 실측 굵기를 그대로 써서 **고유 굵기 값이 41개**가 됐다(실측
jewelry_1_line). "같은 뜻의 선이 같은 굵기"가 깨지고, 디자이너가 굵기를 숫자로 일괄
변경할 수 없다. 스트로크를 내는 모드면 등급화도 건다 — 41개 → **5개**.

### 9-2. 같은 사진이 실행마다 다른 결과를 냈다 — **가장 무거운 것**

외부 조사가 "실무자는 결정성을 신뢰의 조건으로 본다"고 했는데, 정작 우리 파이프라인이
결정적이지 않았다. 같은 사진을 잡 이름만 바꿔 돌리면 결과가 달랐다.

원인은 **외부 모델 응답 캐시를 전부 잡 폴더 안에 둔 것**이었다. 캐시 키는 내용 해시라
같은 입력이면 같은 답을 써야 하는데, 폴더가 달라지면 캐시를 못 찾고 모델을 다시 부른다.
그리고 그 모델들은 매번 다른 답을 준다.

| 무엇 | 실측된 변동 |
| --- | --- |
| GPT 파트 계획 | `engraved_lettering` → `brand_engraving` → `engraved_side_text` |
| Gemini 도면 세그먼트 | `terminal_hallmark` 영역 0개 ↔ 1개 |
| GPT 비전 글자 상자 | 글리프 44,603px ↔ 45,626px |

파트 이름이 바뀌면 글리프 판정이 바뀌고, 글리프가 바뀌면 획과 앵커가 통째로 달라진다 —
같은 사진에서 **앵커가 449 · 454 · 455 · 518 로 흩어졌다.**

세 캐시를 모두 `.cache/` 아래 공유 폴더로 옮겼다(`plan` · `seg` · `letters`).
같은 사진을 다른 잡 이름으로 두 번 돌려 **기하 해시가 완전히 일치**한다.

```
k1  앵커 456 · 프리미티브 93 · 해시 378b1e9a4d02153c
k2  앵커 456 · 프리미티브 93 · 해시 378b1e9a4d02153c
```

**정직하게 밝힐 범위**: 결정적인 것은 **캐시가 채워진 뒤**다. 캐시가 빈 첫 실행은
외부 모델을 부르므로 그 답 자체는 우리가 고정할 수 없다. 즉 "같은 입력 → 같은 출력"은
캐시를 함께 보관할 때만 성립한다.

## 10. v6.4 — 마지막 두 항목과, 실측이 뒤집은 가설

### 10-1. 파트 경계를 넘는 획 병합

획을 파트별로 나눠 추적하므로 부품이 바뀌는 자리에서 반드시 끊겼다. 출고를 두 단계로
갈랐다 — 파트별로 모아 두고, **전역에서 한 번 더** 상호 최선 짝짓기로 잇는다. 이은 획의
레이어는 긴 쪽 부품이 대표하고, 경계를 걸쳤다는 사실은 `shared` 로 남긴다.

실측(jewelry_06): 8쌍 병합, 끊김 18% → 16%. 남은 16%의 상당수는 **굵기가 달라 의도적으로
안 잇는** 쌍이다 — 굵은 윤곽과 가는 디테일을 이으면 stroke-width 하나로 둘 다 틀린 값이
된다.

### 10-2. 구슬 테두리 — 가설이 두 번 뒤집혔다

**가설 1** "구슬 테두리는 한 줄의 물결이다" → 주기 압축(자기상관)을 구현했다.
**실측**: 한 건도 안 걸렸다. 가장 긴 획이 앵커 23개 — 테두리는 물결 한 줄이 아니라
**닮은 작은 획 수백 개**였다(획 337개, 획당 평균 5앵커).

**가설 2** "그럼 닮은 획을 군집으로 묶자" → 형상 정규화 군집을 구현했다.
**실측**: 평균 거리 기준으로 묶으니 선 F@2 가 0.989 → 0.934 로 무너졌다. 최대 거리
기준으로 조이니 게이트는 지키지만 이득이 앵커 32개(-1.4%)뿐이다.

**결론**: 손그림 도면의 구슬은 하나하나 다르다. 형상을 대표로 대체하는 압축은
**품질을 지키면 이득이 미미하고, 이득을 키우면 품질이 무너진다.**

조인 설정조차 안전하지 않았다 — 9종 회귀 검증에서 s_shoe_2 의 작은 디테일 2개가 대표
모티프로 대체되며 2px 밖으로 어긋나 소실됐다(디테일 88% → 75%, 충실도 탈락). 군집 OFF
격리 재실행으로 범인을 확정했다. **군집은 기본 꺼짐(옵트인 `V4_STROKE_CLUSTER=1`)으로
뒤집고**, 주기 압축은 발동 조건이 안 맞으면 아무것도 안 하므로 켜 둔다(`V4_PERIODIC=0`
으로 끔). 이 항목은 "압축 불가"로 닫는다.

### 10-3. 앵커 이력 — 역대 최소인가?

정식 9종, `.ai` 실측 (역대와 같은 펼침 환산 기준):

| 판 | 앵커 |
| --- | ---: |
| V4.7 | 201,431 |
| V4.8 | 75,117 |
| V4.9 | 36,691 |
| V5.0/5.2 | ~29,000 |
| **v6.4 (면 모드)** | **32,432** (저장 기준 30,221) |

**역대 최소가 아니다.** V5.0 보다 ~12% 많다. 다만 그 사이에 V5.0 이 조용히 버리던 내용이
복원됐다 — 검게 채운 면(footwear 검은 갑피 등), 연속성 재주입, bbox 버그로 꺼져 있던
구제. 즉 V5.0 의 29,000 은 **그리다 만 그림의 수치**였다. 같은 내용을 그리는 조건에서의
최소는 v6.4 다. 저장 기준(XObject) 30,221 은 파일에 실제로 든 앵커로는 역대 최소에 가깝다.

### 10-4. 코드 정리

일회용 진단 스크립트 9개 삭제, 측정·감사 스위트 16개는 `server/v4/tools/` 로 이동하고
README 를 붙였다.

## 11. v6.5 — "진짜 필요한 앵커"의 해부

"앵커를 더 줄일 수 있나"에 추측 대신 해부로 답했다.

### 11-1. 앵커는 어디에 사는가 (실측)

| 구성 | 몫 | 판정 |
| --- | --- | --- |
| 획 끝점 (M + 끝) | **37~59%** | 획의 존재 자체 — 획 수를 줄여야 준다 |
| 곡선 중간 앵커 | 41~63% | 솎기 허용오차가 정하는 몫 |

### 11-2. 중간 앵커에는 살이 없다 — 스윕으로 증명

솎기 허용오차를 0.6 → 2.0px 로 올려 봤다(재생성 없이 scene 재적용).

| tol | 앵커 감소 | 최대 이탈 |
| --- | ---: | ---: |
| 0.6 (현행) | 기준 | ≤1.0px |
| 1.0 | **0.5~1.4%** | ≤1.2px |
| 2.0 | 2.6~3.3% | 3.2px (형상 훼손 시작) |

허용오차를 3배로 올려도 1~3%다. **중간 앵커는 이미 곡률이 요구하는 뼈만 남아 있다.**

### 11-3. 스윕이 잡아낸 진짜 버그 2건

처음 스윕에서 "현행 tol 재적용인데 최대 이탈 64.5px" 가 나왔다 — 품질 버그였다.

* **`flatten` 이 직선(L)을 끝점만 샘플** → 긴 직선의 중간이 비어 양방향 이탈 측정이
  변 절반 크기의 가짜 이탈을 보고. 그 가짜 이탈이 멀쩡한 재피팅·솎기를 거부시킨다.
  길이 비례 샘플로 수정.
* **`parsePath` 가 Z 의 닫힘 변을 세그로 안 넣음** → `rotateToSharpest` 가 닫힌 경로를
  회전하면 그 변이 사라져 경로가 찢어질 수 있다. `toCubics` 에서 닫힘 변을 명시하고
  `flatten` 도 닫힘 변을 편다. 수정 후 재현 케이스 이탈 64.5 → 0.5px.

### 11-4. 대시 캐리어 — 스티치를 점선 속성으로

일렬 짧은 획을 "캐리어 패스 + stroke-dasharray" 로 접는다(실무 규범 그대로).
**과대 추정 네 번째**: "대시꼴 700개 = 스티치"라 봤지만 이웃 방향 분포(cos 중앙
0.14~0.6, p25 음수)가 대부분이 방향 뒤죽박죽 질감 조각임을 보였다. 진짜 스티치 줄만

## 12. v6.6 — 얇은 마감(`--thin`): 앵커가 선 안에서 겹쳐 보이지 않게

사용자 피드백: "선을 좀 더 얇게 만들어서 한 개의 선에 앵커가 겹치지 않게."
겹침의 정의를 먼저 수치로 세웠다(`tools/anchorgap.ts`): **이웃 앵커 간격이 그 선의
굵기보다 좁으면 겹쳐 보인다.** 실측 s_jewelry_1 26%, s_shoe_1 14%.

세 가지를 넣었다.

1. **굵기 사다리** (`scene.ts`) — 폭 등급의 위계는 지키되 값을 1.2·2·3.2·4.5·6px 로
   누른다. 도면 실측 굵기(5~35px)를 그대로 쓰면 앵커 점이 선 두께에 파묻힌다.
2. **앵커 최소 간격 강제** (`refit.ts` `enforceAnchorSpacing`) — 선 굵기×1.2 보다
   가까운 이웃 구간을 단일 큐빅으로 병합 시도. 이탈 게이트를 통과할 때만 합치므로
   코너(진짜 필요한 앵커)는 남는다. 병합 불가 구간은 `blocked` 집합으로 건너뛴다
   (첫 실패에서 전체 중단하던 결함 수정).
3. **채점 폭 분리** (`types.ts` `qaWidth` + `qa4.ts`) — 얇기는 표현 선택이다.
   QA 는 누르기 전 등급 폭으로 다시 그려 "경로가 도면과 일치하나"만 묻는다.
   이걸 안 하면 "선 굵기 0.18×" 가짜 벌점(실측 th_shoe_1 F@2 0.56)이 나온다.
   골격 자(lineMode)로 우회하는 안은 해프톤 59% 도면에서 오판(F@3 0.887)이라 기각.

### 12-2. v6.8 — 끝점 잇기 + 선화 도면(`--lineart`) 실험

"얇은 라인이 도형을 온전히 못 이룬다"에 두 갈래로 답했다.

**(1) 끝점 잇기** (`bridgeGaps.ts`, thin 기본 동작) — joinable 의 자(거리 ≤6px,

joinable 지표는 이런 조각을 과대 계상한다.

방식(글자·로고 영역 원본 재합성)이 선행돼야 한다. 옵트인(`--lineart`)으로 둔다.

### 12-3. v6.9 — 선화 재합성(`lineartRecompose`): 크기 고정 + 글자 이식

`--lineart` 의 드리프트 두 가지를 해결했다.

**크기 변화의 원인**: 선화 절이 LoRA 학습 분포를 벗어나며 모델이 재구도한다.
프롬프트에 프레이밍 보존 절을 더하니 생성 자체가 ×0.997~1.002 로 돌아왔고,
그 위에 **결정적 보정**을 얹었다 — 표준 도면과 선화 도면의 주체 박스를
similarityFit 으로 맞춰 선화 도면을 표준 프레임으로 리샘플한다(±2%·4px 안이면
리샘플 생략 — 선을 무르게 만들지 않는다). 프롬프트는 완화, 보정이 보장이다.

**글자 이식**: 표준 도면(같은 입력의 베이크 프롬프트 생성 — 캐시면 공짜)에서 비전
글자 상자를 받아, 선화 도면의 그 자리를 지우고 표준 도면의 잉크만 옮긴다.
- 이식 임계는 100 — 170(inkThreshold)으로 두면 표준 도면의 회색 그라데이션까지
  검은 띠로 따라온다.
- **글자꼴 성분 게이트**: 비전 상자는 직사각형이라 글자 밑 밴드 모서리도 담는다.
  선화 생성이 그 모서리를 굵게 그리면 letterMask 두께 문턱을 넘어 "글리프 면"이
  되어 검은 초승달로 출고됐다(실측 184×708px). 성분 단위로 — 작거나(최장변 <
  캔버스 12%) 도톰하면 글자, 길고 가늘면 선 — 갈라 후자는 중심선으로 돌려보낸다.

### 12-4. v6.10 — Illustrator 실사용 결함 2종 (디자이너 신고)

**① 획 끊김** — "한 줄로 잡혀야 할 부분들이 다 따로 잡힌다."

패스**(최대 4회) — 세 토막 난 한 줄은 한 패스로 못 잇는다.

Illustrator 는 인스턴스 선택 박스를 BBox×행렬로 잡으므로 메시 패턴 인스턴스

### 12-5. 도면 생성 품질 — 굵기·끊김·앵커의 실제 관계 (실측)

**질문**: "외곽 라인이 두꺼우면 벡터화 때 앵커가 많아지지 않나? 선을 충분히 얇게
생성하는가? 우리가 이걸 이용할 수 있나?"

**① 굵기는 앵커를 직접 늘리지 않는다 — 문턱 아래에서는.**
우리는 중심선을 뽑으므로 굵은 선도 패스 하나다. 다만 `evidence.ts` 의
`lineWidthLimit = max(2, round(min(W,H) × 0.012))` 보다 두꺼운 잉크는 **선이 아니라
면**으로 분류돼 윤곽 추적으로 가고, 그때 앵커를 문다. 즉 문턱이 경계다.
9종 상관: 선폭 vs 총앵커 r = **−0.27**, 앵커/획 r = **−0.34** (n=9라 유의하지 않지만
"두꺼울수록 앵커가 많다"는 방향은 **아니다**).

**② 진짜 앵커 동인은 끊김이다.** `go_fast` 실험이 이를 분리해 보여줬다.

| | 잉크% | 폭 중앙 | 최대폭 | 면문턱 초과 | 연결성분 | 앵커 |
| --- | --- | --- | --- | --- | --- | --- |
| jewelry_2 fast | 12.6 | 11.7 | 55.0 | **2.23%** | 4 | 633 |
| jewelry_2 slow | 4.9 | 4.5 | 14.6 | 0.00% | 13 | **495 (−22%)** |
| shoe_2 fast | 15.5 | 4.0 | 24.7 | 0.08% | 764 | 4,370 |
| shoe_2 slow | 10.0 | 4.0 | 19.7 | 0.00% | **5,481** | 6,764 (+55%) |

jewelry_2 는 문턱 초과분(2.23%)이 사라져 앵커가 줄었고, shoe_2 는 메시가 미세
격자로 해상되며 성분이 7배가 되어 앵커가 늘었다. **두 방향이 다 굵기가 아니라
"면 오분류"와 "파편화"에서 왔다.**

**③ 이용법 셋.**
- 요구를 뒤집는다: "얇게 그려달라"가 아니라 **"면 문턱 아래에서 굵고 끊김 없이"**.
  최종 굵기는 어차피 우리 `thinFinish` 사다리가 정한다.
- 느린 경로의 **규칙적 메시가 패턴 압축의 이상적 입력**이다 — 기하 프리미티브 인식이
  61 → **399** 로 6.5배 늘었다. 아직 개별 프리미티브로 나가므로 하나의 반복 패턴으로
  접으면 큰 절감 여지가 남아 있다.
- 문턱을 알고 있으므로 생성 직후 **문턱 초과 비율을 재서** 재생성/경로 선택을
  자동 판단할 수 있다.

**참고**: Replicate `qwen/qwen-image-edit-2511` 은 steps 를 노출하지 않는다
(`go_fast` 토글만). 사내 워커는 KB 문서 기준 **steps=4** 고정이다.
또한 Replicate 는 `aspect_ratio` 기본값이 `match_input_image` 라, VO-522 가 지적한
**square stretch 왜곡을 우리 경로는 이미 피하고 있다**.

### 12-6. v6.11 — 교차점 관통 잇기, 그리고 **전 버전 비교 (반증 포함)**

**가설**: 메시 격자선이 교차점마다 끊겨 앵커를 먹는다. 직진성으로 관통 연결하면
크게 줄 것이다. (근거로 삼은 실측: sf_shoe_2 스트로크 앵커의 51%가 60px 미만 조각,
그중 1,016개가 곧은 열린 조각 = 앵커 2,190개)

**구현**: `junctionPass` — 4갈래 교차점에서는 "상호 최근접"이 전부 거부되므로
거리 대신 **직진성**으로 짝을 고른다(전진 cos·역방향 cos·옆밀림 3중 판정).

**결과: 가설은 대체로 틀렸다.** 문턱 스윕으로 반증했다 — sf_shoe_2 열린 끝점

| --- | --- | --- | --- |
| 12px | 0.1% | 0.6% | 1.6% |
| 26px | **4.6%** | 9.5% | 14.1% |
| 40px | 7.5% | 17.1% | 24.9% |

셀 경계(60~90°로 만나는 사변형 조각)** 였다. 실제 이득은 shoe_2 느린 도면에서

### 14-1. 배경 격리 실패가 조용했다 (2026-09-07 운영 실측)

demo.rebuilderai.com/flat 에 검은 배경 주얼리 사진을 올리니 선 F@2 가 **0.2123** 로 나왔다.
추적한 사슬:

```
fal 계정 잔액 잠금 (HTTP 403 "User is locked. Reason: TOP_UP.")
  → sam3Instances 의 catch { return [] } 가 오류를 삼킴
  → isolateProduct 가 "못 찾음" 으로 원본을 그대로 통과
  → run4 가 그 반환값을 버려서 로그에 한 줄도 안 남음
  → 검은 배경이 그대로 Qwen 도면 모델로
  → 모델이 선화가 아니라 회색 그라데이션 음영 렌더를 반환
  → 벡터화가 배경 그라데이션 띠를 구조선으로 뜸 → 0.21
```

**고친 것 둘.**
1. `run4` 가 격리 결과(`isolated`·`note`)를 `PREPROCESSING` 로그로 흘린다. 여태 버려서
   아무도 몰랐다 — 조용한 실패는 잘못된 결과보다 나쁘다.
2. `flattenUniformBackground` — API 없이 도는 대비책. 테두리에서 **flood fill** 로 이어진
   균일 배경만 흰색으로 바꾼다(임계로 어두운 픽셀을 다 지우면 제품 속이 뚫린다).
   테두리 분산·지워질 넓이(12~92%)를 보고 애매하면 손대지 않는다.

**실측**: jewelry_2(검은 배경) 선 F@2 **0.2144 → 0.849**, 앵커 2,726 → 1,595.
9종 회귀에서 대비책이 실제로 작동한 것은 jewelry_2 하나뿐이고 나머지 8종은 "배경이 이미 밝다"로
건드리지 않았다 — 필요한 곳에서만 도는 것을 확인했다.

**남은 격차 0.849 < 0.95 의 정체**: 거울 반사다. 균일 배경은 지워지지만 제품 아래 반사는
밝기가 달라 남고, 도면 모델이 그것까지 그린다. 이건 SAM 3 이 제 역할을 해야 풀린다
(fal 충전 필요). 대비책은 "치명적 실패를 흔한 실패로" 낮추는 것이지 SAM 3 대체가 아니다.

**B 가 무너진 이유 — 굵기가 다른 획을 이었다.** 코너 후보의 절반 이상이 굵기 등급이 다른 두 획

**옛 매끈 이음도 190쌍이 굵기 불일치로 걸렸고**, 그것들이 v7.0 의 숨은 충실도 손실이었다 —
bag_1 +0.0114 · jewelry_2 +0.0065 · jewelry_3 +0.0061 은 코너 이음이 아니라 이 게이트가 낸 이득이다.

**재피팅은 유지한다.** D↔E: 앵커 −1.9% 에 선 F@2 −0.0002 — 사실상 공짜다. C↔B 도 같다.

**패스는 +2.2% 늘었다.** 굵기 게이트가 막은 잘못된 이음(190)이 코너 이음(123)보다 많아서다.
따로 있는 것이 맞는 패스들이다 — 굵은 선과 얇은 선은 한 패스가 될 수 없다. 다만 "굵기 등급이
한 칸 다른 짧은 토막"은 긴 획의 굵기를 따라가게 이어도 될 것이다 — 다음 과제.

**잡음 바닥**: 세그먼트가 API 라 같은 설정을 두 번 돌려도 앵커가 ±100 흔들린다(jewelry_2 D 884 ·
F 1,009, 이음 수 동일). 한 샘플의 수치가 아니라 9종 방향(F@2 8/9 상승·동일)으로 읽어야 한다.

`inkStrict` 선택은 D↔F 가 잡음 안에서 갈려 실측으로 못 가른다 — 리뷰의 원칙("필터 전 원본 잉크가
근거")을 따랐다. 굵기 게이트 뒤로는 기각이 0~3쌍이라 어느 쪽이든 결과를 거의 바꾸지 않는다.

**v7.1 기본값**: 코너 이음 ≤150°(2갈래) · 잉크 근거 ≥0.6(inkStrict, 먼 다리) · 굵기 동일 게이트 ·
