V4.3 — Semantic Topology Vectorizer · 2026-08-24 · 도면 직접 segmentation (Phase B 1단계)

V4.2 — 외부 딥리서치에서 채택한 것

두 번째 외부 분석(레이어 분리·점 밀도)을 받아 코드 실태와 대조 검증했습니다. 전체 판정과 단계별 계획은 V42_METHOD.md 에 있습니다. 이번에 적용한 것은 신규 API 없이 가능한 Phase A 세 가지입니다.

  • 삭제 직전 디테일 구제. 해프톤 분류가 스티치 점선·로고 문자까지 삼키던 것을, 삭제 직전에 사슬 방향성(길쭉한 대시 + 장축 방향 이웃 + 간격 CV≤0.45)· 크기(점 중앙값의 8배)·구멍(문자) 세 신호로 갈라 살립니다. 니트 코도 길쭉해서 처음엔 shoe_3 에서 9,667px 를 오인 구제해 선 F@2 가 1.000→0.922 로 무너졌습니다 — 이웃 분포 검사(스티치 이웃은 사슬 방향 앞뒤뿐, 직물 코는 전방향)를 넣어 해결했습니다. bag_1 에서 스티치 대시 37개·디테일 14개(7,831px)가 살아나 전체 잉크 F@2 0.895 → 0.912.
  • 닫힌 면도 패턴 후보로. 비즈 알·아웃솔 러그·보석 알은 잉크 성분이 아니라 선이 감싼 면이라 패턴 검출기가 영영 못 봤습니다. 면 군집을 프리미티브 적합보다 먼저 검사합니다 — bag_3 패스 747 → 366 (−51%), shoe_3 739 → 499 (−33%). 단, 면에서 온 패턴은 잉크가 아니므로 QA 에서 FACE_FILL 과 같은 규칙으로 제외해야 합니다(안 하면 흰 돌 내부가 검정 잉크로 잘못 세어져 bag_3 F@2 1.000→0.867 — 실측 후 수정).
  • 원본 좌표 기준 단순화 허용오차. 허용오차 0.8px 가 2배 확대 작업 캔버스에 적용돼 실제로는 0.4px 로 재고 있었습니다. 원본 기준으로 환산해 앵커 합계 123,248 → 114,890 (−6.8%), 충실도 변화 없음.
9종 재실측: 패스 합계 2,800 → 2,179 (−22%) · 서브패스 8,469 → 7,886 · 충실도 회귀 0건 (bag_3·shoe_3 선 F@2 1.000 유지). 채택하지 않은 것 — 파트 crop 별 이미지 재생성(공유 경계 이중 생성) · 곡선 carrier 강제 승격(위상 어긋남 회귀 전력). 다음 단계(Phase B)는 도면 자체를 직접 segment 하는 것으로, Gemini 2.5 Flash polygon + SAM 3 정교화가 필요합니다.

Illustrator 파일 — 레이어가 실제로 나뉘어 옵니다

SVG 는 Illustrator 에서 레이어가 오지 않습니다. 최상위 <g> 는 그냥 그룹이 되고 레이어 패널에는 <Group> 하나만 뜹니다. 테크팩을 쓰는 사람은 레이어 패널에서 파트를 켜고 끄므로 그것으로는 일이 안 됩니다. 그래서 layered.ai 를 따로 굽습니다 — .ai(PDF 호환)의 중첩 OCG 가 Illustrator 에서 레이어·하위 레이어로 복원됩니다.
기능 레이어FILLS · OUTLINES · PRIMITIVES · STITCH · PATTERNS · SHARED_BOUNDARIES
└ 파트 하위 레이어Main upper · Laces · Chain shoulder strap …

레이어 순서는 기능이 먼저입니다. 파트를 최상위로 두면 아래 파트의 선 위로 위 파트의 흰 면이 덮입니다 — 면은 불투명합니다. 보이는 그림이 달라지면 레이어 구조가 아무리 예뻐도 틀린 파일입니다. Illustrator 가 없는 환경을 위해 native-layers.jsx 도 함께 냅니다(파일 > 스크립트로 실행하면 네이티브 레이어·그룹·패스로 재구성됩니다).

.ai 를 세 가지로 검증했습니다

샘플레이어하위레이어 밖 패스 .ai vs SVG IoU선 중간 끊김 통째로 빠진 조각해프톤 제외비
  • 레이어 — .ai 를 되읽어 OCG 트리를 세웁니다. 9종 모두 중첩 깊이 2, BDC/EMC 짝이 맞고, 레이어 밖에 그려진 패스가 0개입니다. 패스 합계도 장면과 정확히 일치합니다.
  • 그림 — Illustrator 가 아닌 제3의 렌더러(poppler)로 .ai 를 굽고 같은 장면의 SVG 와 픽셀로 비교합니다. 우리 코드가 자기 자신을 채점하지 않게 하려는 것입니다. 평균 IoU 0.968, 남은 차이는 두 렌더러의 안티에일리어싱 차이입니다(양방향으로 고르게 납니다).
  • 끊김과 누락 — 도면 선의 골격 중 .ai 가 덮지 못한 구간을 찾아, 양끝이 이어져 있는 끊김과 이웃이 아예 없는 통째 누락을 갈라 셉니다. 제품 구조선에서 끊김은 0곳입니다. 다만 누락은 0이 아니고, 해프톤으로 분류된 영역에서 나옵니다 — 아래 경고를 보십시오.
이 작업에서 실제 버그를 하나 잡았습니다. 공유 경계 레이어는 맨 위에 그려지는데, 거기에 불투명한 흰 면이 올라가 그 아래 선을 지우고 있었습니다. bag_3 은 공유 프리미티브 665개가 전부 FACE_FILL 이라 production.svg 의 잉크가 fidelity.svg 대비 77% 로 줄어 있었습니다 — 이미 배포돼 있던 파일이 다른 그림이었다는 뜻입니다. 면은 올리지 않도록 고쳤고, bag_3 IoU 는 0.747 → 0.952 가 됐습니다.

외부 감사에서 드러난 것 — V4.1 에서 고쳤습니다

가장 큰 것은 실제 렌더링 버그였습니다. 닫힌 면에 적합한 기하 프리미티브를 fill="none" stroke-width="0" 으로 내보내 화면에 아예 없었습니다. 9종 합 329개 — bag_3 70/70, shoe_3 208/208, jewelry_1 1/1 이 전부 보이지 않았습니다. 구멍이 줄고 파트 recall 이 떨어지던 원인입니다.
  • 프리미티브 칠하기를 둘로 나눴습니다. 선에서 온 것은 stroke, 면에서 온 것은 fill. QA 에 “굵기 0이면 invalid” 불변식을 넣었습니다. 수정 후 9종 전부 0개, shoe_3 구멍이 750→750 으로 정확히 일치합니다.
  • 면을 파트에 배정한 뒤에 색을 병합합니다. 화면 전체에서 같은 색끼리 먼저 묶으니 서로 다른 부품의 흰 면이 한 컴파운드 패스가 되고, 그 패스가 결국 파트 하나에만 들어갔습니다 — 가방 몸통·플랩·스트랩이 모두 회색이라 한 레이어로 몰렸습니다. 배정도 경계 좌표 표본이 아니라 면적 겹침으로 합니다.
  • 의미 gate 를 다시 썼습니다. 예전 조건은 평균 precision 과 빈 파트 유무뿐이라 recall·IoU·대응 신뢰도를 안 봤고, 패스가 0인 파트는 평균에서 빠져 큰 파트가 통째로 사라져도 점수가 올라갔습니다. 이제 면 파트와 얇은 선 파트를 나눠 재고(끈·체인·각인을 면 IoU 로 재면 구조적으로 낮습니다), 면적 가중 IoU·주요 파트 최소치·대응 신뢰도를 모두 봅니다. 허용오차도 면 0.1% / 선 0.6% 로 나눴습니다.
  • export 와 QA 가 같은 렌더러를 씁니다. QA 가 패턴을 d 로만 찾아 아예 못 그렸고, 모든 기하 프리미티브를 stroke 로 그려 면 프리미티브를 놓쳤습니다.
  • 편집성을 서브패스로 셉니다. <path> 요소만 세면 컴파운드 패스가 1개로 집계됩니다 — bag_3 은 패스 747 이지만 서브패스 1,835, 한 패스에 1,089개입니다. 길이도 서브패스마다 따로 재야 합니다(이어 붙이면 존재하지 않는 도약이 더해져 앵커 밀도가 낮아집니다).
그 결과 의미 gate 는 9종 모두 REVIEW 입니다. 이전 5/9 PASS 는 거짓이었습니다. 파트 레이어 ownership 은 아직 신뢰할 수 없고, 그것을 이제 QA 가 숨기지 않습니다 — 기준 미달 파트를 이름으로 지목합니다.

임계는 손실을 재고 정했습니다

  • 프리미티브는 최대 잔차만 보면 안 됩니다. 대부분 어긋나는데 한 점만 우연히 가까운 적합도 통과합니다 — 신발 도면에서 351개가 타원으로 승격돼 선 충실도가 0.996 → 0.962로 떨어졌습니다. 평균(rms)도 함께 보고 허용치를 캔버스 최소변의 0.25%로 조였습니다.
  • 패턴은 압축률만 보고하면 안 됩니다. 형상 편차를 0.18까지 허용했더니 작은 성분 보존율이 1.00 → 0.75, 구멍이 317 → 271로 떨어졌습니다. 0.05로 조여 정말 같은 것만 묶습니다. 그래도 비즈 메시 가방은 2,585패스를 줄입니다.
  • 점선은 곧지 않으면 dasharray로 바꿀 수 없습니다. 억지로 바꾸면 점이 제자리를 벗어납니다(주얼리 도면 구멍 38 → 24). 직선성 2% 이내만 승격합니다.
  • 구조선은 stroke가 그 잉크를 다 설명한다는 보장이 없어 사후 검산을 합니다 — 실제로 그려 보고 안 덮인 잉크만 윤곽으로 보탭니다.

아직 남은 것 — 감사가 지적한 P1

  • 라우팅 단위가 connected component 라 너무 큽니다. 제품 선화는 외곽·seam·끈·로고가 서로 닿아 하나의 거대한 성분이 되므로 폭 변동과 교차가 커지고, 결국 전체가 outline 으로 갑니다. 그래서 9종에서 구조적 centerline 이 거의 생성되지 않습니다. junction 을 축약한 graph edge 단위로 라우팅해야 합니다.
  • junction continuity 를 전역으로 풀지 않습니다. 체인을 독립적으로 피팅하므로 같은 교차점에서 시작한 두 곡선이 미세하게 다른 좌표로 끝날 수 있습니다.
  • 가변 폭이 없습니다. stroke 굵기가 체인당 상수 하나입니다.
  • 곡선 스티치를 못 잡습니다. 직선성 2% 이내만 dash 로 승격합니다.
  • 패턴 인스턴스 회전이 0 고정입니다. 서술자는 회전 불변이라 군집은 잘 찾지만, 배치할 때 각도를 복원하지 않습니다.

아직 없는 것

기획서의 topology 엔진(SLD · Deep Sketch Vectorization), differentiable refinement (Bézier · NURBS Splatting), dense correspondence(DINOv3), appearance 분해(COVec)는 모델 가중치와 GPU가 필요해 붙이지 않았습니다. 교차점을 전역으로 푸는 일, 가변 폭, 사진↔도면의 조밀 대응은 그래서 여전히 남아 있습니다. 지금은 그 자리에 어댑터 경계만 두고 현재 경로로 돕니다.

V3.2 는 안정 경로입니다. 그 위에 V4 탭이 따로 있습니다. 외부 감사와 V4 기획서를 받아 검증을 통과한 항목만 V3 안에 반영했습니다. 통과하지 못한 항목은 적용하지 않았고, 그 근거도 아래에 남겼습니다.
V3.0 도면 기반 라인 벡터화 V3.1 외부 감사 반영 — 좌표계·해상도·전처리·QA 재작성 V3.2 V4 기획 검증 반영 — 선 굵기 상한 · 파트별 QA · 공유 경계
V4 기획의 나머지(topology 엔진 · differentiable refinement · dense correspondence)는 SLD / Deep Sketch Vectorization / Bézier Splatting / DINOv3 를 Python 워커로 띄우고 모델 가중치와 GPU 를 붙여야 해서 아직 착수하지 않았습니다.

사진을 먼저 VRINGON schematic 워커로 도면화하고, 그 라인만 기준으로 벡터를 만듭니다. 도면은 흰 배경에 선이 명확하므로 색 클러스터링이 필요 없고, 면과 선이 같은 이진 마스크에서 나와 경계가 정확히 맞물립니다.

왜 이 순서인가. V1·V2는 사진의 그라데이션·질감 위에서 경계를 찾느라 파트가 뭉치거나 쪼개졌습니다. 도면화를 먼저 하면 그 문제가 사라집니다 — 도면의 선이 곧 파트 경계입니다.

샘플 9종

외부 감사 후 고친 것 — 실측 전후

2026-08-22, 외부 벡터화 품질 감사를 받고 파이프라인을 다시 만들었습니다. 지표의 기준을 사용자가 화면에서 보는 도면으로 바꾸자, 예전 QA가 통과시키던 결과가 실제로는 원본과 크게 어긋나 있었습니다.

예전 QA는 자기가 망가뜨린 입력을 기준으로 재고 있었습니다. 벡터화 직전에 도면을 사진 크기로 축소하고 비등방으로 늘린 뒤, 그 왜곡된 이미지와 결과를 비교했습니다. 9종 평균 — 보고 F 0.872 · 왜곡 입력 대비 0.917 · 사용자가 보는 도면 대비 0.620.

고친 것

  • 도면을 건드리지 않는다. 벡터는 도면 좌표계에서 만들고, 사진에서 온 파트 마스크 쪽을 등방 변환으로 옮깁니다. 예전에는 반대로 도면을 사진 bbox에 fit:"fill"로 욱여넣어 x·y를 다른 배율로 늘렸습니다(bag_1 실측 종횡비 왜곡 21%).
  • 배경 검출을 교체. 루미넌스 <245를 전경으로 보던 규칙이 RGB 235짜리 도면 배경을 전경으로 잡아 9종 중 5종에서 bbox가 캔버스 전체로 오판됐습니다. 이제 테두리에서 번지는 배경 flood fill로 잡고, 실패하면 정합을 포기합니다.
  • 모델 해상도를 버리지 않는다. 1024² 결과를 사진 크기(예: 304×433)로 줄여 저장하고 있었습니다 — 모델 픽셀의 12.6%만 남았습니다. 이제 종횡비만 되돌립니다.
  • 작은 성분을 무조건 지우지 않는다. 해프톤으로 승인된 클러스터 안의 점만 지웁니다. 예전에는 스티치·지퍼 이빨·로고 문자가 함께 사라졌습니다.
  • 면과 선의 마스크를 분리. 닫힌 면을 찾으려면 morphological closing이 필요하지만, 같은 마스크로 선까지 그리면 평행선이 붙고 교차점에 혹이 생깁니다.
  • 표현을 hybrid로. centerline은 편집성이 좋지만 작은 디테일을 잃습니다 (shoe_1 실측 보존율 4.5%). 굵기가 안정적인 긴 구조선만 stroke로 올리고 나머지는 채워진 outline으로 남깁니다.
  • 파트 배분을 곡선 샘플링으로. 예전에는 d 문자열의 숫자를 훑어 베지어 제어점까지 좌표로 썼습니다. 제어점은 곡선 위에 없습니다.

2차 — 선 굵기 상한 한 줄 (2026-08-22 저녁)

모든 구조선이 같은 굵기로, 그것도 실제보다 얇게 출고되고 있었습니다. centerline.ts 의 Math.min(6, …) 는 centerline 이 원본 해상도에서 돌던 시절의 값입니다. V3 는 도면을 2~4배로 키운 캔버스에서 추적하므로 실효 상한이 원본 기준 1.5~3px 이 됐고, 실측 centerline 1,854개 중 1,745개(94.1%)가 정확히 6 에 붙어 있었습니다. stroke 가 잉크를 덜 덮으니 남은 잉크를 outline 이 전부 떠맡아 패스가 폭증했습니다.

상한을 선/면을 가르는 기준(min(W,H)×0.012)으로 바꾼 결과 — 9종 합계 패스 12,289 → 8,738 (−29%), 노드 156,502 → 105,337 (−33%), 파일 7.03MB → 5.52MB (−21%). 충실도는 손해가 아니라 이득 쪽입니다: 정확 일치 F@0px 평균 0.811 → 0.839, 선 일치 F@2px 0.976 → 0.975 로 사실상 동률.

함께 확인한 것: 기획서가 지목한 “centerline + outline 이중 표현”은 실측으로 성립하지 않습니다 — 두 래스터의 겹침이 |C∩O|/|C| = 0.000~0.006 이고, 순수 fringe 를 제거해도 충실도가 소수 4자리까지 그대로입니다. residual 을 ink ∧ ¬dilate(covered,1) 로 정의하므로 구조적으로 겹칠 수가 없습니다. 진짜 원인은 굵기 상한 하나였습니다.

9종 실측 — 현재 배포본(V3.2) 기준

아래 카드·SVG·수치가 모두 이 표와 같은 실행 결과입니다.

샘플이전 F@2px현재 F@2px 선 F@2px작은 디테일패스판정

「선 F@2px」는 해프톤 질감 영역을 뺀 값입니다 — 그 자리는 점 대신 톤 면으로 그리는 것이 의도이므로 전체 지표에 넣으면 "선이 빠졌다"로 집계돼 진짜 결함이 묻힙니다. jewelry_3은 도면 자체가 보석을 사진처럼 그라데이션으로 그려 보내 이진 추적의 한계에 걸립니다 — QA가 NEEDS_REVIEW로 표시합니다.

파트 배분은 이제 실제로 측정합니다

perPart.coverage 가 전역 통계의 복제여서 파트마다 값이 전부 같았습니다 (bag_1 8개 파트가 전부 0.9996). 이제 파트 레이어를 하나씩 따로 래스터화해 그 파트의 마스크와 대조합니다 — 위 표의 배분 precision 열입니다. 실측 평균 0.65~0.89 이고, 사진과 생성 도면은 원래 정합되지 않으므로 1 이 될 수는 없습니다. 다만 이제 그 오차를 숨기지 않습니다.

아직 남은 것

  • 교차점(junction)에서 어느 선이 어느 선의 연장인지 전역으로 판단하지 않습니다. centerline 모드에서 분기점에 혹·틈이 남습니다. hybrid가 그 부분을 outline으로 돌려 가리고 있을 뿐입니다.
  • 선 굵기가 체인당 하나의 중앙값입니다. 원근으로 폭이 변하는 스트랩은 정확하지 않습니다.
  • 파트 경계선은 한 파트에 귀속시키되 공유 파트를 data-shared로 표시만 합니다. 별도 공유 레이어로 빼는 것은 하지 않았습니다.
  • 사진 파트 마스크와 생성 도면은 원래 정합되지 않습니다. 등방 변환으로 옮기지만 내부 경계는 근사입니다 — 종횡비 불일치를 QA에 기록합니다.

V2 — 레이어 분리 벡터 SVG (개발계획서 구현)

사진의 픽셀을 그대로 지키면서 파트별 레이어로 나누는 두 번째 파이프라인입니다. 플랫 스케치를 거치지 않고, GPT-5.6이 만든 Layer Manifest를 단일 계약으로 삼아 가시영역 마스크 → amodal 복원 → 재질별 벡터화 → 재합성 검증까지 16단계(S00–S15)를 돕니다.

V1과 목표가 다릅니다. V1은 테크팩용 클린 플랫 도면(원본을 스타일 변환), V2는 원본 충실 재현(원본 픽셀 보존). 아래 표에서 트레이드오프가 그대로 보입니다 — V2는 형상·색 일치가 높고, V1은 패스·노드가 훨씬 적어 편집이 가볍습니다.

V1 ↔ V2 실측 비교

같은 기준 이미지(격리·크롭된 원본)를 두 결과의 최종 SVG를 래스터화해 동일 지표로 측정

샘플경로레이어패스노드 KB실루엣 IoU경계 F색차 ΔE2000

실루엣 IoU·경계 F는 높을수록 원본과 형상이 일치, 색차 ΔE2000은 낮을수록 원본 색에 가깝습니다.

핵심 합성 규칙

생성 모델이 원본을 바꾸지 못하게, 보이는 픽셀은 원본에서 가져오고 가려진 부분만 생성합니다.

M_hidden = clamp(M_amodal − dilate(M_visible, seam_margin), 0, 1)
RGB      = I_original × M_visible + G × M_hidden
Alpha    = union(M_visible, M_hidden)
L        = edge_harmonize(RGB, Alpha, seam_band)

알려진 제약

  • Qwen-Image-Layered-Control은 호스팅 API가 없습니다. 자체 호스팅(80GB GPU)이 전제라 워커를 2백엔드로 만들었습니다 — QWEN_LC_URL이 있으면 레이어별 프롬프트 추출, 없으면 같은 계약을 채우는 대체 백엔드로 동작합니다.
  • 반복 질감이 많은 제품(비즈 메시 가방)은 패스가 1,200개를 넘겨 편집이 무거워집니다. 계획서의 complexity budget이 자동으로 단순화를 강화하지만 한계가 있습니다.
  • 배경이 복잡하거나 반사가 강한 사진은 MVP 입력 범위 밖입니다.

전체 예시 (Node.js)

const BASE = "https://YOUR-HOST", KEY = process.env.FLAT_API_KEY;

const form = new FormData();
form.set("image", new Blob([await fs.readFile("sneaker.jpg")]), "sneaker.jpg");
form.set("categoryHint", "footwear");

const { id } = await (await fetch(`${BASE}/v1/jobs`, {
  method: "POST", headers: { "X-API-Key": KEY }, body: form,
})).json();

let job;
do {
  await new Promise(r => setTimeout(r, 5000));
  job = await (await fetch(`${BASE}/v1/jobs/${id}`, { headers: { "X-API-Key": KEY } })).json();
  console.log(job.progress, job.stages.find(s => s.status === "running")?.label ?? "");
} while (job.status === "running");

if (job.status === "error") throw new Error(job.error);
const ai = await (await fetch(job.files.ai, { headers: { "X-API-Key": KEY } })).arrayBuffer();
await fs.writeFile("result.ai", Buffer.from(ai));

왜 플랫 스케치를 거치는가

사진에는 그림자·반사·직물 질감이 있습니다. 벡터화기는 그걸 전부 형상으로 봅니다. 플랫 스케치로 한 번 옮기면 테크팩과 같은 평면 색면 + 윤곽선이 되어, 이후 단계가 다뤄야 할 대상이 명확해집니다. 같은 이미지에서 면과 선을 함께 뽑기 때문에 선이 면과 어긋나지도 않습니다.

레이어는 어떻게 나누는가

세 가지 도구를 각자 잘하는 범위에서만 씁니다.

amodal 분해
가려진 부분까지 복원한 재질 단위 레이어 — 단, 파트 이름은 모릅니다
색 클러스터 + 연결요소
같은 재질이 떨어져 있으면 별개 파트 (토캡 vs 힐카운터)
객체 분할(SAM 3)
일반 명사만 인식합니다 — sole·shoelace·tongue은 되고 vamp·quarter는 안 됩니다. 되는 것만 경계 보정에 씁니다
이름 배정
비전 모델 + 규칙 폴백(위치·크기·색 사전). 모델이 죽어도 이름이 붙습니다

QA가 파이프라인 안에 있다

레이어를 실제 색으로 다시 쌓아 플랫과 대조합니다. 어긋난 곳이 있으면 그 자리에서 고칩니다: 덮이지 않은 전경 회수, 색이 다른 덩어리 분리, 이름 없는 잔재 정리. 최종 지표는 응답의 qa 필드로 나옵니다.

샘플커버리지배경 침범색차 ΔE레이어패스

커버리지 ≥ 0.8 · 배경 침범 ≤ 0.08 · 색차 ≤ 60 이 통과 기준입니다.

알려진 제약

  • 파트 이름은 비전 모델이 없으면 위치·색 규칙으로만 붙어 거칠어집니다 (Region N이 남을 수 있음).
  • 메시·비즈처럼 반복 질감이 많은 제품은 선 패스가 많아져 Illustrator가 무거워집니다.
  • 한 장의 사진에서 보이지 않는 면(바닥·안감)은 만들 수 없습니다.
