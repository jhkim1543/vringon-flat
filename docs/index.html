실제 생성 결과 9종

아래는 이 파이프라인이 실제로 만든 결과물입니다. 원본은 위키미디어 공용의 실사진이고, 레이어 체크박스를 끄면 그 파트가 사라집니다 — Illustrator에서 열었을 때와 같은 구조입니다.

V3 — VRINGON 플랫스케치 → 라인 기준 벡터화

사진을 먼저 VRINGON schematic 워커로 도면화하고, 그 라인만 기준으로 벡터를 만듭니다. 도면은 흰 배경에 선이 명확하므로 색 클러스터링이 필요 없고, 면과 선이 같은 이진 마스크에서 나와 경계가 정확히 맞물립니다.

왜 이 순서인가. V1·V2는 사진의 그라데이션·질감 위에서 경계를 찾느라 파트가 뭉치거나 쪼개졌습니다. 도면화를 먼저 하면 그 문제가 사라집니다 — 도면의 선이 곧 파트 경계입니다.

샘플 9종

외부 감사 후 고친 것 — 실측 전후

2026-08-22, 외부 벡터화 품질 감사를 받고 파이프라인을 다시 만들었습니다. 지표의 기준을 사용자가 화면에서 보는 도면으로 바꾸자, 예전 QA가 통과시키던 결과가 실제로는 원본과 크게 어긋나 있었습니다.

예전 QA는 자기가 망가뜨린 입력을 기준으로 재고 있었습니다. 벡터화 직전에 도면을 사진 크기로 축소하고 비등방으로 늘린 뒤, 그 왜곡된 이미지와 결과를 비교했습니다. 9종 평균 — 보고 F 0.872 · 왜곡 입력 대비 0.917 · 사용자가 보는 도면 대비 0.620.

고친 것

  • 도면을 건드리지 않는다. 벡터는 도면 좌표계에서 만들고, 사진에서 온 파트 마스크 쪽을 등방 변환으로 옮깁니다. 예전에는 반대로 도면을 사진 bbox에 fit:"fill"로 욱여넣어 x·y를 다른 배율로 늘렸습니다(bag_1 실측 종횡비 왜곡 21%).
  • 배경 검출을 교체. 루미넌스 <245를 전경으로 보던 규칙이 RGB 235짜리 도면 배경을 전경으로 잡아 9종 중 5종에서 bbox가 캔버스 전체로 오판됐습니다. 이제 테두리에서 번지는 배경 flood fill로 잡고, 실패하면 정합을 포기합니다.
  • 모델 해상도를 버리지 않는다. 1024² 결과를 사진 크기(예: 304×433)로 줄여 저장하고 있었습니다 — 모델 픽셀의 12.6%만 남았습니다. 이제 종횡비만 되돌립니다.
  • 작은 성분을 무조건 지우지 않는다. 해프톤으로 승인된 클러스터 안의 점만 지웁니다. 예전에는 스티치·지퍼 이빨·로고 문자가 함께 사라졌습니다.
  • 면과 선의 마스크를 분리. 닫힌 면을 찾으려면 morphological closing이 필요하지만, 같은 마스크로 선까지 그리면 평행선이 붙고 교차점에 혹이 생깁니다.
  • 표현을 hybrid로. centerline은 편집성이 좋지만 작은 디테일을 잃습니다 (shoe_1 실측 보존율 4.5%). 굵기가 안정적인 긴 구조선만 stroke로 올리고 나머지는 채워진 outline으로 남깁니다.
  • 파트 배분을 곡선 샘플링으로. 예전에는 d 문자열의 숫자를 훑어 베지어 제어점까지 좌표로 썼습니다. 제어점은 곡선 위에 없습니다.

2차 — 선 굵기 상한 한 줄 (2026-08-22 저녁)

모든 구조선이 같은 굵기로, 그것도 실제보다 얇게 출고되고 있었습니다. centerline.ts 의 Math.min(6, …) 는 centerline 이 원본 해상도에서 돌던 시절의 값입니다. V3 는 도면을 2~4배로 키운 캔버스에서 추적하므로 실효 상한이 원본 기준 1.5~3px 이 됐고, 실측 centerline 1,854개 중 1,745개(94.1%)가 정확히 6 에 붙어 있었습니다. stroke 가 잉크를 덜 덮으니 남은 잉크를 outline 이 전부 떠맡아 패스가 폭증했습니다.

상한을 선/면을 가르는 기준(min(W,H)×0.012)으로 바꾼 결과 — 9종 합계 패스 12,289 → 8,738 (−29%), 노드 156,502 → 105,337 (−33%), 파일 7.03MB → 5.52MB (−21%). 충실도는 손해가 아니라 이득 쪽입니다: 정확 일치 F@0px 평균 0.811 → 0.839, 선 일치 F@2px 0.976 → 0.975 로 사실상 동률.

함께 확인한 것: 기획서가 지목한 “centerline + outline 이중 표현”은 실측으로 성립하지 않습니다 — 두 래스터의 겹침이 |C∩O|/|C| = 0.000~0.006 이고, 순수 fringe 를 제거해도 충실도가 소수 4자리까지 그대로입니다. residual 을 ink ∧ ¬dilate(covered,1) 로 정의하므로 구조적으로 겹칠 수가 없습니다. 진짜 원인은 굵기 상한 하나였습니다.

9종 실측 (기준 = 사용자가 보는 도면)

샘플이전 F@2px현재 F@2px 선 F@2px작은 디테일패스판정

「선 F@2px」는 해프톤 질감 영역을 뺀 값입니다 — 그 자리는 점 대신 톤 면으로 그리는 것이 의도이므로 전체 지표에 넣으면 "선이 빠졌다"로 집계돼 진짜 결함이 묻힙니다. jewelry_3은 도면 자체가 보석을 사진처럼 그라데이션으로 그려 보내 이진 추적의 한계에 걸립니다 — QA가 NEEDS_REVIEW로 표시합니다.

파트 배분은 이제 실제로 측정합니다

perPart.coverage 가 전역 통계의 복제여서 파트마다 값이 전부 같았습니다 (bag_1 8개 파트가 전부 0.9996). 이제 파트 레이어를 하나씩 따로 래스터화해 그 파트의 마스크와 대조합니다 — 위 표의 배분 precision 열입니다. 실측 평균 0.65~0.89 이고, 사진과 생성 도면은 원래 정합되지 않으므로 1 이 될 수는 없습니다. 다만 이제 그 오차를 숨기지 않습니다.

아직 남은 것

  • 교차점(junction)에서 어느 선이 어느 선의 연장인지 전역으로 판단하지 않습니다. centerline 모드에서 분기점에 혹·틈이 남습니다. hybrid가 그 부분을 outline으로 돌려 가리고 있을 뿐입니다.
  • 선 굵기가 체인당 하나의 중앙값입니다. 원근으로 폭이 변하는 스트랩은 정확하지 않습니다.
  • 파트 경계선은 한 파트에 귀속시키되 공유 파트를 data-shared로 표시만 합니다. 별도 공유 레이어로 빼는 것은 하지 않았습니다.
  • 사진 파트 마스크와 생성 도면은 원래 정합되지 않습니다. 등방 변환으로 옮기지만 내부 경계는 근사입니다 — 종횡비 불일치를 QA에 기록합니다.

V2 — 레이어 분리 벡터 SVG (개발계획서 구현)

사진의 픽셀을 그대로 지키면서 파트별 레이어로 나누는 두 번째 파이프라인입니다. 플랫 스케치를 거치지 않고, GPT-5.6이 만든 Layer Manifest를 단일 계약으로 삼아 가시영역 마스크 → amodal 복원 → 재질별 벡터화 → 재합성 검증까지 16단계(S00–S15)를 돕니다.

V1과 목표가 다릅니다. V1은 테크팩용 클린 플랫 도면(원본을 스타일 변환), V2는 원본 충실 재현(원본 픽셀 보존). 아래 표에서 트레이드오프가 그대로 보입니다 — V2는 형상·색 일치가 높고, V1은 패스·노드가 훨씬 적어 편집이 가볍습니다.

V1 ↔ V2 실측 비교

같은 기준 이미지(격리·크롭된 원본)를 두 결과의 최종 SVG를 래스터화해 동일 지표로 측정

샘플경로레이어패스노드 KB실루엣 IoU경계 F색차 ΔE2000

실루엣 IoU·경계 F는 높을수록 원본과 형상이 일치, 색차 ΔE2000은 낮을수록 원본 색에 가깝습니다.

핵심 합성 규칙

생성 모델이 원본을 바꾸지 못하게, 보이는 픽셀은 원본에서 가져오고 가려진 부분만 생성합니다.

M_hidden = clamp(M_amodal − dilate(M_visible, seam_margin), 0, 1)
RGB      = I_original × M_visible + G × M_hidden
Alpha    = union(M_visible, M_hidden)
L        = edge_harmonize(RGB, Alpha, seam_band)

알려진 제약

  • Qwen-Image-Layered-Control은 호스팅 API가 없습니다. 자체 호스팅(80GB GPU)이 전제라 워커를 2백엔드로 만들었습니다 — QWEN_LC_URL이 있으면 레이어별 프롬프트 추출, 없으면 같은 계약을 채우는 대체 백엔드로 동작합니다.
  • 반복 질감이 많은 제품(비즈 메시 가방)은 패스가 1,200개를 넘겨 편집이 무거워집니다. 계획서의 complexity budget이 자동으로 단순화를 강화하지만 한계가 있습니다.
  • 배경이 복잡하거나 반사가 강한 사진은 MVP 입력 범위 밖입니다.

REST API

비동기 잡 방식입니다. 한 건에 2~5분이 걸리므로 생성 요청은 즉시 202로 돌아오고 상태를 폴링합니다.

1. 잡 생성 POST /v1/jobs

curl -X POST https://YOUR-HOST/v1/jobs \
  -H "X-API-Key: $KEY" \
  -F "image=@sneaker.jpg" \
  -F "style=color" \
  -F "layerDetail=standard" \
  -F "categoryHint=footwear"

# 202 Accepted
{ "id":"0f7d1b23-…", "status":"running",
  "statusUrl":"https://YOUR-HOST/v1/jobs/0f7d1b23-…", "pollAfterMs":5000 }

전체 예시 (Node.js)

const BASE = "https://YOUR-HOST", KEY = process.env.FLAT_API_KEY;

const form = new FormData();
form.set("image", new Blob([await fs.readFile("sneaker.jpg")]), "sneaker.jpg");
form.set("categoryHint", "footwear");

const { id } = await (await fetch(`${BASE}/v1/jobs`, {
  method: "POST", headers: { "X-API-Key": KEY }, body: form,
})).json();

let job;
do {
  await new Promise(r => setTimeout(r, 5000));
  job = await (await fetch(`${BASE}/v1/jobs/${id}`, { headers: { "X-API-Key": KEY } })).json();
  console.log(job.progress, job.stages.find(s => s.status === "running")?.label ?? "");
} while (job.status === "running");

if (job.status === "error") throw new Error(job.error);
const ai = await (await fetch(job.files.ai, { headers: { "X-API-Key": KEY } })).arrayBuffer();
await fs.writeFile("result.ai", Buffer.from(ai));

왜 플랫 스케치를 거치는가

사진에는 그림자·반사·직물 질감이 있습니다. 벡터화기는 그걸 전부 형상으로 봅니다. 플랫 스케치로 한 번 옮기면 테크팩과 같은 평면 색면 + 윤곽선이 되어, 이후 단계가 다뤄야 할 대상이 명확해집니다. 같은 이미지에서 면과 선을 함께 뽑기 때문에 선이 면과 어긋나지도 않습니다.

객체 분할(SAM 3)
일반 명사만 인식합니다 — sole·shoelace·tongue은 되고 vamp·quarter는 안 됩니다. 되는 것만 경계 보정에 씁니다
이름 배정
비전 모델 + 규칙 폴백(위치·크기·색 사전). 모델이 죽어도 이름이 붙습니다

QA가 파이프라인 안에 있다

레이어를 실제 색으로 다시 쌓아 플랫과 대조합니다. 어긋난 곳이 있으면 그 자리에서 고칩니다: 덮이지 않은 전경 회수, 색이 다른 덩어리 분리, 이름 없는 잔재 정리. 최종 지표는 응답의 qa 필드로 나옵니다.

샘플커버리지배경 침범색차 ΔE레이어패스

커버리지 ≥ 0.8 · 배경 침범 ≤ 0.08 · 색차 ≤ 60 이 통과 기준입니다.
